## 1. llm-d-showroom — 캐시 인식 라우팅으로 tail latency 개선

**개요**: 동일 하드웨어에서 단순 수평확장(round-robin) 대비 llm-d의 지능형 라우팅으로 P95/P99 TTFT를 극적으로 줄일 수 있음을 벤치마크로 입증.

**다루는 주제**
- KServe + vLLM으로 Llama 3.1 8B 단일 GPU 배포, KV 캐시·prefill/decode 단계 이해
- Prometheus/Grafana + GuideLLM으로 성능 관측·벤치마크
- vLLM 4 레플리카 수평확장 + ClusterIP round-robin 기준선 수립 (캐시 히트율 20~30%)
- llm-d `LLMInferenceService` 배포 + 3개 스코어러(prefix-cache 3 / queue 2 / active-request 2) → 캐시 히트율 60~80%, TTFT p95 24s→478ms

**enabler 핵심**: GPU를 더 사는 것(throughput↑)이 tail latency를 악화시킬 수 있다는 역설. 반복 prefix(시스템 프롬프트·공유 문서) 워크로드에서 캐시 인식 라우팅이 결정적. → [[01-분산추론과-llm-d]]

## 2. llmaas-showroom — 중앙 LLM 서비스(LLMaaS) 운영

**개요**: LLM을 일회성 실험이 아닌 **운영 인프라**로 다루는 Platform Engineering 관점. GPU 풀링·개발자 생산성·운영 자동화·비용 추적까지 LLMaaS 전 생애주기.

**다루는 주제**

**enabler 핵심**: 멀티테넌시(네임스페이스 격리), 토큰 단위 과금, GPU 풀링으로 유휴율↓. "모델을 클러스터 내부에만 노출"하는 보안 우선 설계. → [[07-LLMaaS-MaaS-멀티테넌시]]

## 4. llamastack-on-ocp — Llama Stack으로 에이전트 단계별 구축

**개요**: RHOAI 위에서 Llama Stack으로 RAG부터 시작해 웹검색·ReAct·MCP·자동 인시던트 대응까지 점진적으로 복잡한 에이전트를 만든다 (Level 0~6).

**다루는 주제**

- Level 5 MCP(OpenShift/Slack 서버) → Level 6 통합 자동 인시던트 대응(분석→검색→인프라조작→Slack 보고)
- 모델: Granite 3.2 8B(로컬 vLLM) + Llama 3.2 3B(원격)

**enabler 핵심**: Llama Stack = 추론·RAG·에이전트·안전성·텔레메트리를 표준 API로 묶는 "비즈니스 로직 계층". → [[02-Llama-Stack-핵심]]
