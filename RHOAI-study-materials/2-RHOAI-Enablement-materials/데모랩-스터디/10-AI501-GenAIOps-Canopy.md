## 1장. LLM이 실제로 어떻게 동작하나 (The AI Orientation)

GenAIOps의 모든 의사결정은 "모델이 왜 이렇게 동작하나"의 이해에서 출발한다.

### 모델의 정체
- 언어모델 = 결국 **파라미터(숫자 가중치)를 담은 바이너리 파일.** 학습 때 익힌 패턴이 이 숫자들에 인코딩돼 있고, 입력 텍스트를 출력 텍스트로 매핑하는 블랙박스.
- **파라미터 많음 = 더 똑똑하지만 더 느림.** 큰 모델은 연산(행렬곱)이 많아 하드웨어를 더 쓰고 응답이 느리다. 그래서 모델 크기 선택은 항상 "지능 ↔ 속도/비용" 트레이드오프.
- **GPU가 CPU보다 훨씬 빠르다** — 핵심 연산이 행렬곱인데 GPU가 그걸 가속하도록 설계됐기 때문.

### 텍스트 생성 = 자기회귀(autoregressive)
한 번에 문장을 만드는 게 아니라 **토큰 하나씩** 만든다:
1. 현재 텍스트(프롬프트 + 지금까지 생성분)를 입력으로
2. "다음에 올 토큰"의 확률 분포 계산
3. 확률 높은 토큰 선택
4. 그 토큰을 붙이고 → 1로 반복

즉 모델은 **"학습 데이터에서 이 맥락 다음에 통계적으로 가장 그럴듯한 토큰"**을 고를 뿐. 그래서 출력이 매끄러워 보이는 건 "이해"가 아니라 "통계적으로 자연스러운 연속".

### 컨텍스트 윈도우
- **최대 컨텍스트 길이 = 프롬프트 + 생성 출력 둘 다 포함.** 많이 생성할수록 원래 프롬프트가 들어갈 "공간"이 줄어든다. → 무한정 정보를 넣을 수 없음(RAG·프롬프트 설계가 "선별"인 이유).

### 모델의 4가지 습성(mannerisms)
1. **반응형(Reactive)**: 입력(프롬프트)이 없으면 아무것도 출력 안 함. 커피머신처럼 요청해야 동작.
2. **비결정적(Non-deterministic)**: 생성에 무작위성이 들어가 **같은 프롬프트도 매번 다른 답**.
3. **확률 기반 = 할루시네이션의 근원**: 지식을 "가진" 게 아니라 그럴듯한 다음 토큰을 **자신 있게** 생성. 예) "원주율의 마지막 두 자리"처럼 답이 없는 질문에도 당당히 답을 지어냄. *"앵무새가 뜻도 모르고 들은 말을 반복"*하는 것에 비유.
4. **지속 기억 없음**: 세션 간 정보를 기억 못 함. 매 대화는 백지에서 시작(사용자 입력으로 학습하지 않음).

### 할루시네이션의 메커니즘과 대응
- 원인: **맥락이 부족하면 "그럴듯하지만 틀린" 연속을 고른다.** 모델은 사실 검증을 안 하고 패턴 매칭만 한다.
- 대응: **관련 맥락을 충분히 주입** → 그래서 RAG(관련 문서를 프롬프트에 끼워넣기)가 강력. → [[01장 핵심 연결: RAG는 6장]]

> 💡 딜리버리 포인트: 고객이 "왜 답이 매번 달라요/왜 거짓말해요"라고 할 때 ① 비결정성 ② 확률 기반 생성 ③ 컨텍스트 부족 으로 설명하고, **해법은 프롬프트→RAG→가드레일 순의 계층**이라고 안내.

## 2장. 프롬프팅 (Linguistics — 기초)

**프롬프팅 = 모델에서 답을 끌어내는 유일한 입력 수단.** 텍스트만 받으므로 표현이 곧 품질.

### System 프롬프트 vs User 프롬프트
- **System 프롬프트**: 모델의 행동/맥락을 정의(*"너는 친절한 튜터다"*). 앱 개발자가 작성, 사용자에겐 안 보임, **User보다 우선**.
- **User 프롬프트**: 실제 질문/작업(*"5+5는?"*).
- 핵심 규칙: **모델은 System을 User보다 더 따른다**(그렇게 학습됐기 때문). 단 "더 따른다"지 "절대 강제"는 아님 → 그래서 가드레일이 필요(7장).

### 맥락 주입(Context Injection)
프롬프트 안에 정보를 직접 넣어 답을 유도할 수 있다. 모델은 그 사실을 "학습"하는 게 아니라 **그 대화 동안만** 사용. 대화가 길어지면 이전 응답이 다음 입력에 누적돼 연속성이 생김(= 멀티턴). 단 **컨텍스트 윈도우 한계** 안에서만.

### Temperature(창의성 다이얼)
- **0 = 결정적·진지함**(가장 확률 높은 토큰 위주), **1 = 창의적·무작위**.
- 요약·추출 같은 작업은 낮게, 브레인스토밍은 높게. Prompt Playground에서 system/user/temperature를 바꿔가며 출력 변화를 체득하는 게 핵심 실습.

## 3장. 프롬프트 엔지니어링 & 버저닝 + GitOps

### 프롬프트 엔지니어링 = "유용·정확한 출력을 끌어내는 입력 설계"
- 같은 모델도 표현(톤·구체성·형식)에 따라 결과가 완전히 달라진다.
- 기법: 역할 부여(System), 제약 명시(길이·형식), 예시 제공(few-shot), 단계적 사고 유도. 반복 테스트로 최적 프롬프트를 찾는다.

### 프롬프트 버저닝 — 왜 중요한가
- 문제: 프롬프트 실험이 **노트북·채팅에 흩어져 추적 불가·재현 불가·재사용 불가.** 프롬프트는 "재사용 가능한 코드 컴포넌트"처럼 다뤄야 한다.
- 해법: **MLflow Prompt Registry** = 프롬프트를 중앙 저장 + 메타데이터(노트/태그/버전) + 런타임에 특정 버전 호출 + 협업/감사.
- 워크플로: 프롬프트 생성 → 커밋 메시지와 함께 등록(Version 1) → 자동 버전 번호·`latest` 태그 → 앱(Canopy)이 런타임에 등록된 프롬프트를 fetch. **= 프롬프트를 "코드처럼" 버전관리.**

### GitOps (Ready to Scale 101)
GenAIOps 배포의 토대. 세 원칙:
1. **선언적 desired state**: "어떻게"가 아니라 "무엇이 되어야 하는가"를 YAML로 선언.
2. **Git = 단일 진실 원천**: 모든 설정·배포 정의·모델/프롬프트 버전이 Git에. 모든 변경이 커밋 이력으로 감사 가능.
3. **지속적 reconciliation**: **ArgoCD**가 Git의 desired state와 클러스터 실제 상태를 계속 비교, 어긋나면 자동 적용.
- GenAIOps 의미: **모델·프롬프트를 test→prod로 안전·재현가능하게 승격.** 수동·실수 잦은 배포를 자동·추적가능하게. → [[06-GitOps-ValidatedPatterns-PoC배포]]
- 모델 호출은 **OpenAI 호환 API**(OpenAI Python SDK)로 — 생태계 도구 즉시 연동.

## 4장. GenAI 앱 평가 (Ready to Scale 201)

"프롬프트 바꿀 때마다 자동 평가 → 게이트 → 배포"가 GenAIOps의 심장.

### 평가의 3계층
1. **모델 평가**: 앱 로직과 무관한 raw LLM 능력.
2. **백엔드 평가**: 앱 구현(프롬프트·오케스트레이션·데이터 흐름) 포함 전체.
3. **컴포넌트 평가**: 워크플로 각 조각을 블랙박스가 아닌 **개별 단위로** 테스트.

### Expectations + Scorers 프레임워크
- **Expectations(기대)**: 특정 입력/프롬프트에서 "어떤 출력을 원하는가"를 정의(예: 요약은 200자 미만).
- **Scorers(채점기)**: 실제 출력이 기대를 충족하는지 측정(예: "요약문이 목표 길이보다 짧은가").
- **평가 데이터셋 만들기**: 프로덕션 trace 중 대표 샘플 선별 → 기대값 주석 → 데이터셋으로 묶어 → 시스템에 돌려 점수 수집. (도구: MLflow 평가)

### 성능 메트릭(속도)
- **TTFT**(Time To First Token, 첫 응답 지연), **TPOT**(토큰당 생성 속도), **Throughput**(동시 처리량). 복잡도가 커질수록 use-case 적합성 판단에 필수. (도구: GuideLLM) → [[06-LLM-벤치마킹-GuideLLM-가이드]]
- **LLM-as-Judge**: 정답이 정형화 안 되는 생성물은 또 다른 LLM이 채점(질문에 충실한가, 기대 답과 모순 없는가).

## 5장. RAG — 근거 있는 AI (Grounded AI)

### 왜 RAG인가 (LLM의 3대 한계 보완)
1. **지식 컷오프**: 학습 시점 이후 사건을 모름.
2. **할루시네이션**: 불확실하면 그럴듯하게 지어냄.
3. **사설 데이터 접근**: 사내 문서·정책 등 학습에 없던 자료.

→ RAG = **관련 정보를 질문과 함께 주입하고 "이 정보 기반으로 답하라"고 지시** → 답을 사실에 "grounding".

### RAG 동작(인덱싱 → 런타임)
프롬프트 구조 = `[System 역할] + [검색된 컨텍스트] + [User 질문]`. 5단계 파이프라인:
1. **Chunking(청킹)**: 문서를 적당 크기 조각으로 분할(너무 크면 느리고 노이즈, 너무 작으면 맥락 손실).
2. **Embedding(임베딩)**: 각 청크를 의미를 담은 **벡터(숫자 배열)**로 변환.
3. **Storing**: 벡터를 벡터DB에 저장.
4. **Retrieving**: 질문도 임베딩 → **의미적 유사도**로 가까운 청크 검색(키워드 매칭이 아니라 "뜻"으로 찾음 = semantic search).
5. **Generating**: 검색된 청크를 프롬프트에 넣어 LLM이 답 생성.
- 핵심 제약: **컨텍스트를 적게 넣을수록 빠르다** → "관련성 높은 것만 똑똑하게 선별"이 RAG의 본질.

### 임베딩 & 벡터DB(Milvus)
- **임베딩** = 텍스트의 의미를 좌표 공간의 점(벡터)으로. 의미가 비슷하면 벡터가 가깝다 → 코사인/거리로 유사도 측정.
- **벡터DB** = 수백만 벡터를 효율 저장·검색하도록 최적화된 DB. **Milvus**(고성능 오픈소스)를 RHOAI에 Helm으로 배포, **Attu**(웹UI)로 벡터 탐색. (로컬 변수보다 훨씬 확장적)

### Docling (문서 지능)
- 문제: 일반 RAG는 표·수식·차트·다단 레이아웃 같은 **비텍스트 요소**에 약함.
- **Docling** = PDF 등 비정형 문서를 **구조(섹션·계층·표·수식)를 보존한 머신리더블 형식**으로 변환하는 전처리기. 청킹/임베딩 전에 끼워 더 똑똑한 분할·임베딩을 가능케 함. → 학술/기술 문서 RAG 품질↑.

### RAG 평가 (3 스코어)
1. **Answer Quality**: 답이 질문에 맞고 기대답과 모순 없는가.
2. **Retrieval Relevance**: 가져온 청크가 질문과 관련 있는가.
3. **Retrieval Groundedness**: LLM이 **실제로 검색 청크를 근거로** 답했는가(아니면 무시하고 지어냈는가).
- ⚠️ RAG 평가는 **RAG 전용 judge 프롬프트** 필요 — 일반 기준으로 채점하면 "검색 문서에서 가져온 정당한 답"을 부당하게 깎음.

## 6장. 관찰성 & 피드백 루프 (The AI Watcher)

전통 관찰성(메트릭/로그/트레이스)은 **시스템 건강**을 보여주지만, AI 앱에서 진짜 중요한 건 **출력 품질** — 그건 사용자 피드백만이 알려준다.

### 관찰성 스택
- **Prometheus**(메트릭·알림) + **Grafana**(대시보드) + **OpenTelemetry Collector**(벤더중립 텔레메트리 수집) + **LokiStack**(로그 집계) + **Tempo**(트레이싱) + OpenShift User Workload Monitoring. → [[04-AI-보안-관찰성-기초]]

### 피드백 루프 = GenAIOps의 빠진 고리
1. **수집**: 응답마다 👍/👎 이진 신호("이 요약 도움됐나요?").
2. **trace에 저장**: 피드백을 **MLflow trace에 `user_satisfaction`(true/false)**으로 부착 — 그 프롬프트·응답·지연·모델 메타데이터 바로 옆에. 별도 시스템 불필요.
3. **부정 피드백 → 테스트 케이스화**: `user_satisfaction=false` trace를 필터 → 사람이 검토해 "더 나은 답"을 정의 → **회귀 테스트(평가 기대값)**로 전환.

### A/B 테스트 (Champion/Challenger)
- **Champion**(현 프로덕션 프롬프트) vs **Challenger**(새 버전)를 동시 배포, 사용자가 둘 중 선호 선택 → `ab_preference`로 기록 → 일관되게 이기면 Champion으로 승격. **코드 변경 없이** 프롬프트 교체.

### 닫힌 루프
`배포 → 관찰 → 피드백 수집 → 평가 데이터셋 구축 → 프롬프트 개선 → 재배포 → 반복`. 데모와 프로덕션의 차이 = **사용자에게서 체계적으로 배우는가.**

## 7장. 가드레일 (The Honor Code)

### 가드레일이란 & 왜 필요한가
- 가드레일 = 모델 행동을 제약하는 안전장치(의도 범위 밖 질문 거부, 부적절·편향 응답 차단). Canopy 예: 학생이 정답을 그냥 캐내려는 시도 차단(학업 부정 방지).
- **System 프롬프트만으론 부족**: 프롬프트는 "모델 컨텍스트 안의 제안"일 뿐 강제력이 없다. 확률적이라 **프롬프트 인젝션·우회·긴 대화로 무시될 수 있음.** → **모델 바깥의 계층적 강제**가 필요.

### 가드레일 아키텍처 (계층 방어)
- **프롬프트 레벨**: 빠르지만 불안정(첫 줄 방어).
- **외부 강제 계층**: 입력 전 필터 / 출력 후 필터 / 분류기 / 정책 엔진 / allow·deny 리스트. **"바라지 말고 강제하라(enforce, don't hope)".**

### NeMo Guardrails + Colang
- **NeMo Guardrails** = 미들웨어. 모든 요청은 LLM 도달 전, 모든 응답은 사용자 전달 전 검사.
- **Colang** = 입력/출력 흐름(rails)을 선언적으로 정의하는 DSL. 설정은 배포 Helm 차트에 포함.
- **6종 탐지기(순차 동작)**:
  1. 정규식 패턴 매칭(특정 금지 문구)
  2. **HAP 탐지**(혐오·욕설·비속어) — **Granite Guardian**
  3. **프롬프트 인젝션 탐지** — **DeBERTa** 기반
  4. **언어 검증**(영어 강제) — **Lingua**
  5. **민감정보(PII)** 탐지(금융·개인 식별자)
  6. **LLM-as-Judge**가 애매한 엣지케이스 최종 판정(특화 탐지기가 놓친 것).
- **자동화 테스트**: **Spikee**로 프롬프트 인젝션을 자동 시도해 가드레일이 뚫리는지 벤치마크. → [[04-에이전트-AI-패턴]]

## 8장. 에이전트 (Autonomous Systems 101)

### 에이전트 vs 일반 챗봇
- 챗봇 = 학습 데이터만으로 답(과거에 갇힘). **에이전트 = LLM + 도구(tools)** → 실시간 데이터 조회·API 호출·계산 등 현실과 상호작용.
- 핵심: **LLM은 "무엇을 언제 할지" 결정**하고, **실제 도구 실행은 백엔드가** 함(모델은 외부 호출을 직접 하지 않음). 모델은 추론에 집중, 시스템이 실행 담당.

### 에이전트 루프 = ReAct (Reason–Act–Observe)
4단계 반복:
1. **Thought(추론)**: 도구를 쓸지/어떤 걸 쓸지 "소리내어 생각".
2. **Action(행동)**: 적절한 도구 호출(백엔드가 실행).
3. **Observation(관찰)**: 결과를 받음.
4. **반복**: 작업 완료까지.
- 왜 동작하나: **"생각을 말로 풀게" 하면 도구 선택이 좋아지고 스스로 오류를 잡는다.** 고정 경로가 아닌 **구조화된 자율성**이 더 나은 결과.

### 도구(Tools) & 함수 호출 & MCP
- **도구** = JSON 인터페이스로 감싼 서비스(API·DB·계산기). 모델은 추측 대신 도구를 호출해 실데이터를 받음.
- 흐름: 사용자 요청 → 모델이 어떤 도구·어떤 파라미터인지 결정(JSON 생성) → **백엔드가 실제 실행** → 결과를 모델에 반환 → 모델이 해석해 응답.
- **도구 스키마(JSON)**: 도구가 뭘 하고, 어떤 파라미터를 받고, 어떤 형식을 반환하는지 정의 → 모델이 도구별 커스텀 지시 없이 올바르게 호출.
- **MCP(Model Context Protocol)**: 여러 관련 도구를 한 서버로 묶음("도구 하나"가 아니라 "도구상자"). 로컬/원격 실행 가능, 도구 모음을 조직·배포하기 쉽게. → [[03-MCP-핵심]]

### Agentic 워크플로
- 도구 경로를 하드코딩("A 다음 B")하지 않고 **LLM에 순서 결정 자율권**을 줌. **LangGraph** = 그래프 기반으로 복잡 워크플로(상태·분기·반복)를 오케스트레이션하는 프로덕션 프레임워크. ReAct 외에도 plan-then-execute, 병렬 탐색, self-critique 등 패턴 존재.

### 에이전트 평가 (3계층)
1. **도구 단위 테스트**: 각 도구(캘린더 API·검색 등)를 통합 전 개별 검증.
2. **Text→JSON 검증**: LLM이 **도구 호출 JSON을 올바르게 포맷**하고 **맞는 도구를 고르는가**(잘못된 JSON·도구 오선택이 주요 실패점).
3. **End-to-End**: 전체 워크플로가 사용자를 돕는가. **Tool-use correctness**(예상 도구를 실제로 호출했나 — trace로 "어떤 도구를 어떤 순서로" 추적) + **Task completion** + **LLM-as-Judge**(생성답이 질문에 충실·기대답 대비 정확한가). → [[02-Llama-Stack-핵심]], [[04-에이전트-AI-패턴]]

### Model Card 읽기 (HuggingFace)

### CPU vs GPU 서빙 & vLLM/KServe
- **CPU 서빙**: 느리지만 **개발·데모·저트래픽엔 충분**. 기밀 제약 시 합리적.

- 예: 개발은 Llama 3.2 3B로 하다 온프렘 제약 때문에 **TinyLlama 1.1B(CPU)**로 다운스케일 — 능력 일부를 포기하고 기밀·인프라 제약에 맞추는 실전 판단.
- ⚠️ **이 장이 우리 non-GPU 학습플랜과 직결** — CPU 서빙 흐름 재현 가능. → [[RHOAI-학습플랜-non-GPU]], [[05-vLLM-추론엔진-핵심정리]]

## 10장. 모델 압축/양자화 (The Fitness Program)

동기: 고성능 모델이 "$500/day GPU"를 먹는 현실 → **품질 유지하며 더 작고 빠르고 싸게.**

### 양자화란 (수치적으로)
- 정밀도를 낮추는 압축: 가중치를 16bit 대신 8/4bit로 **반올림.** *"$14.37을 $14로 반올림"* 비유.
- 공식: **`q = round(x / scale) + zero_point`**
  - `x`=원본값(FP32), `q`=양자화 정수(INT8), `scale`=스텝 크기, `zero_point`=비중심 분포 보정 이동.
  - 예: 0.375, scale=0.125 → q = round(0.375/0.125) = 3.
- 포맷: FP16 / INT8 / INT4 / **W8A16**(가중치 8bit·활성 16bit) 등. **가중치(weights)와 활성(activations)을 따로** 다룬다.

### PTQ(사후 양자화) & 캘리브레이션
- **캘리브레이션 데이터** = 압축 알고리즘에 "정상값이 어떤 모습인지" 가르치는 대표 입력. 없으면 **중요한 값을 뭉개버림**("눈 감고 사진 압축").
- 흐름: 학습된 모델 로드 → 대표 데이터 통과 → 활성값 범위 학습 → 재구성 오차 최소화하며 가중치 압축 → 내보내기.

### 입도(Granularity) — 몇 개 값이 scale 하나를 공유?
- **Per-tensor**: 레이어 전체가 scale 1개 — 가장 빠름·메타데이터 최소·정확도 최저.
- **Per-channel**: 채널마다 scale — 정확도↑, 오버헤드 중간.
- **Group(g128/g64/g32)**: 작은 청크마다 scale — **정확도 최고**(작을수록 좋음), 메타데이터↑. "각 자에 맞는 눈금."

### 정확도 회복 기법
- **대칭 vs 비대칭**: 대칭(scale만, 0중심 가중치용) / 비대칭(scale+zero_point, ReLU 후 항상 ≥0인 활성용).
- **이상치(outlier) 대응**:
  - **SmoothQuant**: 활성의 어려움을 가중치로 수학적으로 이전(활성×smoothing, 가중치÷같은 인자).
  - **AWQ**: 활성 패턴상 **중요한(salient) 채널**을 식별해 보호.
  - **Mixed precision**: 민감 레이어는 FP16 유지, 나머지만 양자화.
- **Saturation(클리핑) 방지**: 현실적 데이터로 캘리브레이션, 더 미세한 입도, clipping 최소화 scale.

### 도구
- **llm-compressor** = "양자화 맥가이버칼"(여러 알고리즘, HF 호환, vLLM 서빙용 출력). oneshot API + `GPTQModifier`(scheme/targets/ignore)로 소량 코드.
- 압축 후 **반드시 평가**: **lm-evaluation-harness**(업계표준 벤치로 "안 망가졌나" 검증) + **GuideLLM**(지연/처리량/TTFT). vLLM/KServe 서빙 + ArgoCD로 test→prod 승격. → [[03-LLM-모델-양자화-압축-핵심정리]]

## 11장. MaaS — Models-as-a-Service (Supply & Demand 101)

### 문제: GPU 직접 배분의 낭비
- 부서마다 GPU 직접 주면 **각자 같은 모델을 따로 배포** → "7명이 7개 Llama를 7 GPU에 띄우고 각 3% 사용률", 동시에 다른 쪽은 "자원 없음". 1.9만 직원 규모면 자원 호딩·중복으로 병목.

### 해법: 모델을 서비스로 중앙화
- *"GPU 접근을 주지 말고 **모델 접근**을 주자."* → **전문가가 관리하는 1개 배포를 1 GPU에서 70%+ 가동.**
- **멀티테넌시 3계층**: Admin / AdminReadonly / User(API 소비만).
- **API 키 기반 접근**(인프라 자격증명 아님) → 세밀한 제어·사용량 추적.

- **OpenAI 호환 게이트웨이**: **LiteLLM Proxy**가 여러 백엔드를 단일 OpenAI 호환 API로 통합 → 기존 도구 그대로, 백엔드는 교체 가능.

## 12장. 파인튜닝 (The Tuning Room)

### 언제 무엇을? (프롬프팅 vs RAG vs 파인튜닝)
- **프롬프팅/RAG**: 동적 정보·일회성 커스터마이즈. 최신 데이터 접근, 유연한 행동 요구일 때.
- **파인튜닝**: 다음일 때 —
  - 모델이 **일관된 행동**을 해야 함
  - **도메인 전문 용어**가 필요
  - **프롬프트가 너무 길어짐**
- 예: 소크라테스식 행동을 위한 **800토큰 system 프롬프트 → 파인튜닝 후 ~10토큰**(행동이 "가중치 안에 구워짐"). → 토큰 비용↓·탈옥 취약성↓.

### LoRA (Low-Rank Adaptation)
- 전체 네트워크가 아니라 **소수 파라미터(어댑터)만 업데이트** → 성능 유지하며 연산·시간 대폭 절감. 자원 제약 환경의 핵심. base 모델 + 어댑터를 vLLM이 동적으로 함께 서빙.

### 합성 데이터(SDG)
- 파인튜닝은 보통 **500~1000+ 예시** 필요한데 좋은 데이터는 구하기 어렵다 → **SDG Hub**가 LLM으로 합성 학습데이터 생성(수작업 라벨링 없이 가능).

### 워크플로
합성데이터 생성(+Docling으로 문서→마크다운) → **Training Hub(Unsloth 백엔드)로 LoRA 학습** → 오프라인 평가(lm-evaluation-harness, 베이스라인 대비) → 레지스트리 저장·배포(ArgoCD로 Canopy 반영). → [[02-모델-학습-파인튜닝-기초]]

- **GenAIOps의 한 줄 요지**: 프롬프트·RAG·가드레일·에이전트·모델을 **버전관리 + 자동평가 + 피드백루프 + GitOps 배포 + 관찰성**으로 묶어 "데모"를 "운영 시스템"으로.
- **계층적 신뢰성**: 할루시네이션/오남용 대응은 ① 프롬프트 → ② RAG(맥락) → ③ 가드레일(외부 강제) → ④ 평가/피드백 루프 순.
- **거의 전부 GPU 필요**하나 9장 CPU 서빙은 non-GPU 플랜에서 재현 가능.
- **MaaS 구분**: LiteMaaS(PoC) vs 정식(Kuadrant/Limitador+Redis).
- ⚠️ 이 노트는 lab README/페이지 기반 **2차 학습정리** — 실행 검증 전. 홈랩 SNO에서 일부 돌려보면 "검증됨"으로 격상.
