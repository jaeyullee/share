# LLM 추론 필요 VRAM 계산법

> LLM을 GPU(또는 MIG 슬라이스)에 올리기 전, 메모리가 들어가는지(fit) 판단하기 위한 계산법.
> 메모리 fit이 **먼저**, 연산 성능 매칭이 그다음.

---

## 계산 공식

### 전체

```
필요 VRAM ≈ (가중치) × 1.2 + (KV 캐시)
            └ 오버헤드 +20% ┘
```

- `× 1.2` = 활성값(activation) · CUDA 컨텍스트 · 프레임워크 · 메모리 단편화 여유(고정 오버헤드 근사)

### ① 가중치 (Weights)

```
가중치(GB) = 파라미터수(B) × 정밀도바이트
```

### ② KV 캐시

```
KV 캐시(바이트) = 2 × 레이어수 × KV헤드수 × head_dim × 정밀도바이트 × 컨텍스트길이 × 동시사용자수
```

- 맨 앞 `2` = **K(Key)와 V(Value)를 각각 캐시**하기 때문
- `KV헤드수 × head_dim` = **KV 차원(kv_dim)** 으로 묶어서 봐도 됨

### 빠른 현장 어림셈 (FP16 가정)

```
필요 GB ≈ 파라미터수 × 2.5
```
- `2(바이트) × 1.2(오버헤드) ≈ 2.4`에 KV 약간 얹어 반올림
- 예: 7B → 약 18GB, 70B → 약 175GB
- ⚠️ 롱컨텍스트(32K+)·고동시성이면 KV가 폭증하므로 어림셈 금지 → ② 별도 계산

## 변수값 분류 및 설명

변수는 **모델이 고정하는 값**과 **사용 방식이 결정하는 값**으로 나뉜다.

### A. 정밀도바이트 (dtype) — 데이터 타입이 결정

`×2`는 **FP16 가정**일 뿐, 양자화하면 바뀐다. 양자화가 메모리를 줄이는 원리.

| 정밀도 | 바이트/param | 7B 가중치 |
|---|---|---|
| FP32 | 4 | 28GB |
| **FP16 / BF16** | **2** | 14GB |
| FP8 / INT8 | 1 | 7GB |
| INT4 | 0.5 | 3.5GB |

> KV 캐시도 별도로 양자화 가능(KV cache FP8 → KV 단가 절반).

### B. 모델이 고정하는 값 — "토큰당 단가"

모델 아키텍처(모델 카드)로 정해져 바뀌지 않는다.

| 변수 | 의미 | 메모 |
|---|---|---|
| 파라미터수 | 모델 크기(B) | 가중치의 본체 |
| 레이어수 | 트랜스포머 블록 수 | 많을수록 KV↑ |
| KV헤드수 | `num_key_value_heads` | **어텐션 구조가 결정 (아래 표)** |
| head_dim | 헤드당 차원 | `hidden_size ÷ 헤드수`로 역산 가능 |

#### 어텐션 구조에 따른 KV 단가 차이 (같은 파라미터수여도 천차만별)

| 방식 | KV 헤드 | 상대 KV 크기 |
|---|---|---|
| **MHA** (구형) | 전체 (예: 32) | 기준 (큼) |
| **GQA** (Llama3·Qwen 등 대부분) | 그룹 (예: 8) | 1/4~1/8 |
| **MQA** | 1 | 최소 |
| **MLA** (DeepSeek) | 잠재벡터 압축 | 매우 작음 |

> 그래서 KV 단가는 파라미터수만으론 안 나온다. **모델 스펙(GQA 여부 등)을 봐야 한다.**

### C. 사용 방식이 결정하는 값 — "토큰 수량"

운영자가 통제하는 레버. 같은 모델도 이 값에 따라 KV가 몇 배씩 출렁인다.

| 변수 | 의미 | 통제 방법 |
|---|---|---|
| 컨텍스트길이 | 프롬프트 + 생성 토큰 (seq_len) | `max context length` 제한 |
| 동시사용자수 | 동시 처리 요청(batch) | 동시요청 수 제한 |

> KV는 토큰 수에 **완전 선형**: 컨텍스트 2배 = KV 2배, 사용자 2배 = KV 2배.

---

## 워크된 예시

### 가중치 (FP16)

| 모델 | 계산 | × 1.2 | 가중치 소요 |
|---|---|---|---|
| 7B | 7×2=14 | 16.8 | 약 17GB |
| 13B | 13×2=26 | 31.2 | 약 31GB |
| 70B | 70×2=140 | 168 | 약 168GB (A100 80GB ×2도 빠듯) |

### KV 캐시 (Llama 3 8B — GQA: 32레이어, KV헤드 8, head_dim 128, FP16)

토큰당 = `2 × 32 × 8 × 128 × 2` = **약 128KB/토큰**

| 상황 | KV 캐시 |
|---|---|
| 1명 × 8K 컨텍스트 | 약 1GB |
| 10명 동시 × 8K | 약 10GB |
| 1명 × 128K 롱컨텍스트 | **약 16GB** (가중치만큼 커짐) |

---

## 실무 적용 순서 (MIG 슬라이스 배치 등)

1. **가중치 계산** = 파라미터수 × 정밀도바이트 (고정)
2. **KV 예산 계산** = 토큰당 단가 × (목표 컨텍스트길이 × 목표 동시성) ← **SLA에 맞춰 설계**
3. `(가중치 × 1.2 + KV)` 합이 **슬라이스/카드 메모리 안에 들어오게** 프로파일 선택
4. 메모리 통과 후 → 연산 성능(latency/throughput) 매칭

### KV 줄이는 레버

| 종류 | 방법 |
|---|---|
| 모델 선택 | GQA/MLA 모델, **KV 캐시 양자화(FP8)** |
| 사용 제한 | max context length 제한, 동시요청 수 제한 |
| 서빙 기법 | **PagedAttention**(단편화 없이 KV 알뜰 관리) |
