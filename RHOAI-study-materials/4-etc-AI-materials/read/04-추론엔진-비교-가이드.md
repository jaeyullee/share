# 추론 엔진 비교 가이드 (vLLM vs llama.cpp vs Ollama)

> 어떤 추론 엔진을 언제 써야 하는가. OCP 엔지니어 관점에서 각 엔진의 특성과 선택 기준을 정리한다.

---

## 1. 세 엔진 한눈에 비교

| 항목 | vLLM | llama.cpp | Ollama |
|------|------|-----------|--------|
| 설계 철학 | 고처리량, 프로덕션 서빙 | 경량, 이식성, 단일 스트림 | 개발 편의성, 로컬 실험 |
| 언어 | Python | C/C++ | Go |
| GPU 의존성 | GPU 필수 (CPU도 가능하나 비권장) | CPU 우선, GPU 선택 | CPU/GPU 모두 |
| 동시성 처리 | 매우 강함 (continuous batching) | 약함 (큐잉 모델) | 기본 제한적 (튜닝 가능) |
| OpenAI 호환 API | 있음 | 있음 | 있음 |
| 설치 복잡도 | 중간 | 낮음 | 매우 낮음 |
| 프로덕션 적합성 | 높음 | 낮음 | 낮음 |

---

## 2. 벤치마크 수치로 보는 차이

### vLLM vs llama.cpp (A100 기준, Llama 계열)

| 동시성 | vLLM TPS | llama.cpp TPS | 배율 |
|--------|---------|--------------|------|
| 1 | 비슷 | 비슷 | ~1x |
| 16 | 크게 증가 | 거의 변화 없음 | ~10x |
| 최대 | 최대 TPS | 정체 | **44배** |

- **TTFT**: vLLM은 낮고 안정적, llama.cpp는 동시성 증가 시 기하급수적으로 악화
- **ITL**: 낮은 동시성에서는 vLLM이 낮음, 높은 동시성에서는 llama.cpp가 낮음 (단, 이는 요청을 제한해서 활성 작업 수를 줄인 결과)

### vLLM vs Ollama (A100-PCIE-40GB, Llama 3.1 8B)

| 항목 | vLLM | Ollama |
|------|------|--------|
| 최대 TPS | **793** | **41** |
| 최대 TPS 시 P99 지연 | **80ms** | **673ms** |
| 동시성 256에서 TTFT | 낮고 안정 | 급격히 상승 |

Ollama를 `OLLAMA_NUM_PARALLEL=32`로 튜닝해도 vLLM이 모든 구간에서 우세했다.

## 3. 언제 무엇을 쓰나

### vLLM을 선택할 때

```
✓ 여러 사용자가 동시에 쓰는 API 서버
✓ 고트래픽 챗봇, 실시간 대화형 서비스
✓ OpenShift/Kubernetes 프로덕션 배포
✓ 처리량과 확장성이 최우선
✓ 엔터프라이즈 GPU 환경 (A100, H100, L40S)
```

**OCP 비유**: 프로덕션 Deployment. 오토스케일링, 모니터링, 고가용성이 필요한 환경.

### llama.cpp를 선택할 때

```
✓ 단일 사용자 또는 저동시성 작업
✓ 로컬 개발, 데스크톱 앱, 임베디드/엣지 디바이스
✓ GPU 없는 환경 (CPU 전용)
✓ 빠른 시작 시간, 낮은 자원 사용량
✓ 오프라인 배치 처리
```

**OCP 비유**: 개발자 로컬 환경의 `oc` CLI. 서버가 아니라 개인 도구.

### Ollama를 선택할 때

```
✓ 로컬 개발 및 프로토타이핑
✓ 모델 빠르게 실험해보고 싶을 때
✓ 설치 복잡도를 최소화하고 싶을 때
✓ 단일 사용자 환경
```

**OCP 비유**: `podman play kube`처럼 빠르게 띄워보는 도구. 프로덕션용이 아님.

## 4. CPU 추론: 가능하지만 제한적

vLLM은 GPU 없이 CPU로도 실행 가능하다. 단, 프로덕션 용도로는 권장하지 않는다.

**실험 환경**: OpenShift 4.18, 베어메탈, GPU 없음, Llama-3.2-1B-Instruct

**핵심 발견**:
- CPU 추론은 **메모리 대역폭 제약** 워크로드다
- 단일 NUMA 노드에 고정하면 오히려 성능 저하 (IPC 0.52)
- 두 NUMA 노드 인터리빙 시 성능 향상 (IPC 1.20)
- IPC < 1은 CPU가 계산보다 메모리 대기에 더 많이 묶임을 의미

**결론**: CPU 추론은 기능 검증/프로토타이핑에는 유용하지만, 실제 서비스에는 GPU가 필수다.

## 5. Red Hat AI Inference Server (RHAIIS)

Red Hat이 vLLM을 기반으로 엔터프라이즈 지원을 추가한 제품이다.

```bash
# 이미지 pull
podman pull registry.redhat.io/rhaiis/vllm-cuda-rhel9:3

# 로컬 실행 예시
podman run -d \
  --device nvidia.com/gpu=all \
  -p 8000:8000 \
  -v ~/rhaiis-cache:/opt/app-root/src/.cache:Z \
  --shm-size=4g \
  registry.redhat.io/rhaiis/vllm-cuda-rhel9:latest \
  --model RedHatAI/Llama-3.2-1B-Instruct-quantized.w8a8
```

**OCP 비유**: vLLM이 upstream Kubernetes라면, RHAIIS는 OpenShift. 같은 코어에 엔터프라이즈 지원과 보안 강화가 추가됐다.

### RHAIIS 통합 사례

| 통합 대상 | 방법 | 용도 |
|---------|------|------|
| Claude Code | `ANTHROPIC_BASE_URL` 환경변수 | 로컬 모델로 Claude Code 백엔드 교체 |
| LangChain/LangGraph | OpenAI 호환 API 연결 | 에이전트 워크플로 구성 |
| Whisper | `/v1/audio/transcriptions` 엔드포인트 | 음성-텍스트 변환 |
| Voxtral | `/v1/realtime` WebSocket | 실시간 스트리밍 ASR |

## 6. OpenShift 배포 패턴

### 단순 배포 (Deployment + Service + Route)

```yaml
# 핵심 설정만
containers:
- image: registry.redhat.io/rhaiis/vllm-cuda-rhel9:3
  args:
  - --model
  - meta-llama/Llama-3.2-1B-Instruct
  resources:
    limits:
      nvidia.com/gpu: "1"
```

### KServe + Knative (오토스케일링)

```yaml
# InferenceService 핵심 설정
annotations:
  serving.kserve.io/deploymentMode: Serverless
  autoscaling.knative.dev/metric: concurrency
  autoscaling.knative.dev/target: "13"
  autoscaling.knative.dev/panic-threshold-percentage: "150"
spec:
  minReplicas: 1
  maxReplicas: 3
```

**OCP 비유**: 단순 배포는 Deployment, KServe+Knative는 HPA + KEDA 조합과 비슷하다.

## 7. RHEL 이미지 모드: OS까지 컨테이너로

AI 추론 스택 전체(모델 + 서버 + 앱 + OS)를 하나의 bootc 이미지로 패키징한다.

```
bootc 이미지
├── RHEL 9 (OS)
├── llamacpp_python (모델 서버)
├── Mistral 7B GGUF (모델)
└── chatbot (앱)
```

배포 대상: 컨테이너, AWS AMI, qcow2 VM, 베어메탈(Kickstart)

**OCP 비유**: CoreOS가 OS를 이미지로 관리하듯, bootc는 AI 스택 전체를 이미지로 관리한다. 업데이트도 레지스트리 push로 처리된다.

## 8. 엔진 선택 결정 트리

```
프로덕션 서비스인가?
├── 예 → 동시 사용자가 많은가?
│         ├── 예 → vLLM (또는 RHAIIS)
│         └── 아니오 → vLLM (소규모도 vLLM 권장)
└── 아니오 → 로컬 실험/개발인가?
              ├── 빠른 시작 원함 → Ollama
              ├── CPU 전용 환경 → llama.cpp
              └── GPU 있고 성능 테스트 → vLLM
```

## 핵심 요약 (3줄)

1. 고동시성 프로덕션 서비스는 vLLM, 로컬/엣지/단일 사용자는 llama.cpp, 빠른 실험은 Ollama다.
2. 최대 부하에서 vLLM이 Ollama 대비 TPS 19배, llama.cpp 대비 44배 우세하다.
3. OpenShift 환경에서는 RHAIIS(vLLM 기반)를 KServe+Knative로 배포하면 오토스케일링까지 자동화된다.
