# vLLM 추론 엔진 핵심 정리 (OCP 엔지니어 관점)

> OCP를 아는 사람이 vLLM을 이해하기 위한 핵심 정리. "LLM을 서빙하는 엔진"이 어떻게 동작하고 어떻게 튜닝하는지를 OCP 운영 경험으로 풀어낸다.

---

## 1. vLLM이 뭔가

**vLLM = LLM 전용 고성능 추론 서버**

OCP에서 Deployment + Service + Route를 만들어 앱을 서빙하듯, vLLM은 LLM 모델을 GPU에 올려서 OpenAI 호환 API(`/v1/chat/completions`)로 서빙한다.

| OCP 개념 | vLLM에서 대응 |
|---------|-------------|
| 컨테이너 런타임 (CRI-O) | vLLM 추론 엔진 |
| Deployment | vLLM 서버 프로세스 |
| Service/Route | OpenAI 호환 API 엔드포인트 |
| 리소스 제한 (limits) | `--max-num-seqs`, `--gpu-memory-utilization` |
| HPA (오토스케일링) | 복제본(replica) 수 조정 |

핵심 차별점은 **PagedAttention**이다. 일반 메모리 할당처럼 KV 캐시를 고정 크기로 잡지 않고, OS의 페이지 테이블처럼 동적으로 할당한다. 덕분에 메모리 낭비가 줄고 동시 처리 요청 수가 크게 늘어난다.

---

## 2. 추론의 두 단계: Prefill vs Decode

LLM 추론은 두 단계로 나뉜다. 이걸 모르면 성능 문제를 잘못 진단한다.

| 단계 | 하는 일 | 특성 | OCP 비유 |
|------|--------|------|---------|
| **Prefill** | 입력 토큰 전체를 한번에 처리해 KV 캐시 생성 | 연산 집약적, 병렬 처리 가능 | 빌드(build) 단계 |
| **Decode** | KV 캐시를 읽어 토큰을 하나씩 생성 | 메모리 대역폭 제약, 순차 처리 | 런타임 서빙 단계 |

**TTFT(Time To First Token)** = 대기 시간 + Prefill 시간  
**ITL(Inter-Token Latency)** = Decode 단계 속도

TTFT가 높으면 Prefill 병목 또는 큐 적체, ITL이 높으면 Decode 병목이다.

---

## 3. KV 캐시: 성능의 핵심

KV 캐시는 LLM이 이전 토큰들의 상태를 GPU 메모리에 저장해두는 공간이다.

**비유**: OCP의 etcd처럼 "지금까지 처리한 상태"를 저장한다. 이게 꽉 차면 새 요청을 받을 수 없다.

```
GPU 메모리 구성
├── 모델 가중치 (고정, 수십~수백 GB)
└── KV 캐시 (동적, 요청마다 증가)
    └── 꽉 차면 → 새 요청 대기 → TTFT 급증
```

**Prefix Caching**: 같은 시스템 프롬프트를 쓰는 요청들이 KV 캐시를 공유한다. vLLM V1에서 기본 활성화됐다. OCP의 이미지 레이어 캐시와 같은 개념이다.

---

## 4. vLLM V1 엔진: 무엇이 달라졌나

V1은 V0의 기술 부채를 전면 재설계한 버전이다. v0.8.0부터 기본값이 됐다.

| 항목 | V0 | V1 |
|------|----|----|
| 프로세스 구조 | 스케줄러 + Worker 0 같은 프로세스 | EngineCore 별도 프로세스 분리 |
| CPU 작업 처리 | Worker 0에서 블로킹 처리 | 토크나이징/전처리 비동기 병렬 처리 |
| Prefix Caching | 기본 비활성화 (오버헤드 큼) | 기본 활성화 (오버헤드 1% 미만) |
| 입력 준비 | 매 스텝마다 텐서 재생성 | Persistent Batch로 변경분만 갱신 |
| 스케줄링 | Prefill/Decode 구분 | 토큰 단위 통합 스케줄링 |

**성능 향상 수치 (v0.7.3 대비)**:
- Llama 3.1 8B, 생성 중심 워크로드: **최대 24.5% 처리량 향상**
- Llama 70B, 생성 중심 워크로드: **최대 14.6% 처리량 향상**
- 멀티모달(Qwen2-VL): **최대 40% 처리량 향상**

## 5. 성능 튜닝: 3개 파라미터만 기억하면 된다

### 핵심 튜닝 레버

| 파라미터 | 기본값 | 역할 | 언제 조정 |
|---------|--------|------|---------|
| `--gpu-memory-utilization` | 0.9 | GPU 메모리 중 KV 캐시에 쓸 비율 | KV 캐시 부족 시 올림 (최대 0.95~0.97) |
| `--max-num-seqs` | 256 | 동시 처리 최대 요청 수 | 처리량 정체 + 지연 급증 시 낮춤 |
| `--kv-cache-dtype` | auto | KV 캐시 정밀도 | 메모리 부족 시 `fp8`로 낮춤 |

### 튜닝 순서 (OCP 트러블슈팅처럼 접근)

```
1. 실제 워크로드와 유사한 데이터셋 준비 (GuideLLM 사용)
2. TTFT / ITL / P99 지연 기준선 측정
3. KV 캐시 점유율 확인 → 90% 이상이면 메모리 부족
4. --gpu-memory-utilization 점진 상향 (0.90 → 0.93 → 0.95)
5. 필요 시 --kv-cache-dtype fp8 적용 (품질 검증 필수)
6. 처리량 정체 지점 찾아 --max-num-seqs 설정
```

### 성능 진단 흐름

```
TTFT 높음 ──→ 대기 요청(waiting) 있음? ──→ 서버 포화 → 복제본 추가
              ↓ 없음
              긴 프롬프트? → Chunked Prefill 확인

ITL 높음 ──→ 배치 크기 과도? → --max-num-seqs 낮춤
             메모리 대역폭 한계? → GPU 업그레이드 또는 TP 확장
```

## 6. GPU 배치 전략: 복제본 vs 텐서 병렬

같은 GPU 8장을 쓸 때 어떻게 배치하느냐에 따라 성능이 달라진다.

| 구성 | 특성 | 적합한 경우 |
|------|------|-----------|
| TP=8, 복제본 1개 | 모델 하나를 8 GPU에 분산 | 모델이 너무 커서 4 GPU에 안 들어갈 때 |
| TP=4, 복제본 2개 | 4 GPU짜리 2개 인스턴스 | 처리량 우선, 장애 격리 필요 |
| TP=2, 복제본 4개 | 2 GPU짜리 4개 인스턴스 | 고동시성, 스케줄링 유연성 우선 |

**원칙**: 모델이 들어가는 최소 TP를 쓰고, 나머지는 복제본으로 확장한다. TP가 늘면 GPU 간 통신 오버헤드가 생기기 때문이다.

**실측 예시 (Llama 70B)**:
- TP=1 → TP=2 전환 시 KV 캐시 블록 923개 → 12,830개 (13.9배)
- 처리량 2,282 tok/s → 8,967 tok/s (3.9배, GPU 2배 대비 초선형 향상)

## 7. 구조화된 출력 (Structured Output)

LLM 응답을 JSON, 정규식, 선택지 등으로 강제하는 기능이다.

| 방식 | 파라미터 | 용도 |
|------|---------|------|
| JSON 스키마 | `guided_json` | 구조화된 객체 반환 |
| 정규식 | `guided_regex` | 날짜, 식별자 등 고정 포맷 |
| 선택지 | `guided_choice` | 분류 태스크 |
| 문법 | `guided_grammar` | SQL 쿼리 생성 등 |

동작 원리: 토큰 생성 시 유효하지 않은 토큰을 마스킹한다. 백엔드는 XGrammar(반복 스키마에 유리)와 Guidance(동적 스키마에 유리) 중 자동 선택된다.

## 8. 2:4 스파스 모델: 더 작고 빠른 추론

**2:4 구조적 희소성** = 4개 가중치 중 2개를 제거하는 압축 기법. NVIDIA Ampere 이상 GPU에서 하드웨어 가속된다.

| 항목 | 수치 |
|------|------|
| 정확도 복구율 | 98.4% (Open LLM Leaderboard 기준) |
| 단일 스트림 가속 | 최대 3.0배 (A5000/A6000 기준) |
| 처리량 향상 | 1.2배~1.8배 |
| 희소성 단독 기여 | 약 1.1배~1.2배 |

**비유**: OCP에서 불필요한 컨테이너 레이어를 제거해 이미지를 경량화하는 것과 비슷하다. 기능은 유지하면서 크기를 줄인다.

---

## 핵심 요약 (3줄)

1. vLLM은 PagedAttention + continuous batching으로 GPU 메모리를 효율적으로 쓰는 LLM 추론 서버다.
2. V1 엔진은 CPU 오버헤드를 줄이고 prefix caching을 기본화해 최대 24% 처리량을 높였다.
3. 성능 튜닝은 TTFT/ITL 진단 → KV 캐시 점유율 확인 → 3개 파라미터 조정 순서로 접근한다.
