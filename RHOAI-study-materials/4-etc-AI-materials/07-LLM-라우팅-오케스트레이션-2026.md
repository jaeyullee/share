# LLM 라우팅·오케스트레이션 정리: RouteLLM, Semantic Router, LangGraph

> 2026-06-26 | RouteLLM·Semantic Router·LangGraph 중심 | 공개 공유용

---

## 1. 한 줄 결론

2026년 LLM 애플리케이션 스택은 단순히 "어떤 모델을 쓸까"에서 **요청마다 어떤 모델·도구·워크플로우·관찰성 경로를 태울까**로 이동하고 있다.

핵심 축은 세 가지다.

| 축 | 대표 도구 | 주 역할 | 언제 중요한가 |
|---|---|---|---|
| 모델 라우팅 | RouteLLM, vLLM Semantic Router, LiteLLM, Portkey | 요청을 비용·품질·안전 기준으로 적절한 모델/엔드포인트에 보냄 | 모델 풀이 여러 개이고 비용·지연·보안 차이가 클 때 |
| 에이전트 오케스트레이션 | LangGraph, LangChain, AutoGen, CrewAI | 멀티스텝 추론, 도구 호출, 상태 저장, 사람 승인 흐름 구성 | 단발 QA가 아니라 업무 절차를 자동화할 때 |
| 관찰성·평가 | MLflow, LangSmith, Phoenix, Langfuse, Helicone, AgentOps | trace, tool call, prompt, cost, eval, replay 관리 | 운영 중 실패 원인과 품질 회귀를 추적해야 할 때 |

실무적으로는 `LangGraph`로 업무 흐름을 만들고, 그 안의 모델 호출은 `RouteLLM`/`Semantic Router`/`LiteLLM` 같은 라우터 또는 게이트웨이에 위임하며, 전 구간을 `MLflow`/`LangSmith`/`Langfuse`류로 trace하는 구조가 자연스럽다.

## 2. 개념 구분

### 2-1. Routing과 Orchestration은 다르다

**Routing**은 "이 요청을 어디로 보낼까"의 문제다.

예시:

- 쉬운 질문은 작은 모델로 보낸다.
- 어려운 추론은 reasoning 모델로 보낸다.
- 개인정보가 들어간 요청은 외부 API로 보내지 않는다.
- 이미지 입력은 multimodal 모델로 보낸다.
- 특정 intent는 LLM 호출 없이 정해진 tool로 보낸다.

**Orchestration**은 "업무를 어떤 순서와 상태로 실행할까"의 문제다.

예시:

- 사용자 질문 → RAG 검색 → 답변 초안 → 검증 → 필요 시 재검색.
- 티켓 분석 → 원인 후보 생성 → 명령 실행 승인 요청 → 결과 요약.
- 여러 agent가 분담하고 중간 상태를 저장하며 실패 시 재개.

즉, `RouteLLM`과 `Semantic Router`는 주로 **모델/요청 라우팅 계층**이고, `LangGraph`는 **상태ful workflow/agent 오케스트레이션 계층**이다.

### 2-2. 운영 스택에서의 위치

```text
[User / App]
   |
   v
[LangGraph workflow]
   |-- 상태 저장, 재시도, human-in-the-loop
   |-- tool call / RAG / sub-agent 호출
   |
   v
[LLM Gateway / Router]
   |-- RouteLLM: strong/weak 모델 비용 라우팅
   |-- Semantic Router: intent/safety/domain/model routing
   |-- LiteLLM/Portkey: provider 호환성, fallback, budget, logging
   |
   v
[Serving backends]
   |-- vLLM / SGLang / Ollama / llama.cpp
   |-- OpenAI / Anthropic / Bedrock / Azure / Gemini 등
   |
   v
[Observability / Eval]
   |-- trace, token, cost, latency, prompt version, eval, replay
```

OCP 관점으로 보면 `LangGraph`는 애플리케이션 내부의 workflow controller에 가깝고, `Semantic Router`/`RouteLLM`은 Ingress/Gateway 또는 sidecar/ext_proc에 가까운 정책 계층이다. `vLLM`은 실제 모델 서빙 runtime, `MLflow`/`LangSmith`/`Langfuse`는 trace와 품질 회귀를 보는 관찰성 계층이다.

## 3. 도구별 핵심 정리

### 3-1. RouteLLM

**정체**: LMSYS 계열의 LLM router 프레임워크. 강한 모델과 약한 모델 사이에서 요청별로 어느 모델을 쓸지 결정한다.

핵심 아이디어:

- 모든 요청을 비싼 모델로 보내면 품질은 높지만 비용이 커진다.
- 모든 요청을 싼 모델로 보내면 비용은 낮지만 어려운 요청에서 품질이 떨어진다.
- RouteLLM은 prompt를 보고 "강한 모델이 이길 확률"을 추정해 threshold보다 높으면 강한 모델, 낮으면 약한 모델로 보낸다.

공식 README 기준 주요 특징:

- OpenAI client 대체 또는 OpenAI-compatible server 방식으로 붙일 수 있다.
- trained router를 제공하며, MT-Bench 등에서 비용을 최대 85% 줄이면서 GPT-4 성능의 95%를 유지하는 결과를 제시한다.
- `mf`, `sw_ranking`, `bert`, `causal_llm`, `random` router를 제공한다.
- 평가 벤치마크는 `mmlu`, `gsm8k`, `mt-bench`를 지원한다.
- LiteLLM을 활용해 여러 provider와 local/OpenAI-compatible endpoint를 연결한다.

RouteLLM을 쓰기 좋은 상황:

| 상황 | 이유 |
|---|---|
| 강한 모델/약한 모델 2단 풀이 명확함 | RouteLLM의 기본 가정이 strong vs weak 모델 선택 |
| 비용 절감이 1차 목표 | request별 escalation으로 expensive model 호출 비율을 줄임 |
| 자체 traffic 샘플로 threshold를 보정할 수 있음 | threshold calibration이 실제 workload 분포에 민감 |
| gateway 전체보다 router 연구/평가가 중요함 | serving, fallback, logging은 별도 조합 필요 |

주의할 점:

- RouteLLM 단독은 full production gateway가 아니다. fallback, budget, auth, audit, cache, 관찰성은 별도 계층이 필요하다.
- 공개 데이터 기준 threshold를 쓰면 실제 업무 트래픽에서 strong model 비율이 예상과 달라질 수 있다.
- `mf`/`sw_ranking` router는 embedding 생성 요구사항이 있으므로 폐쇄망·로컬 모델 환경에서는 embedding endpoint까지 함께 설계해야 한다.

### 3-2. Aurelio Semantic Router

**정체**: LLM이 답변을 생성하기 전에 embedding/vector similarity로 intent route를 빠르게 결정하는 Python 라이브러리.

핵심 아이디어:

- "도구를 쓸지 말지" 또는 "어떤 prompt/chain으로 보낼지"를 매번 LLM에게 물으면 느리고 비싸다.
- 미리 route별 예문 utterance를 정의하고, 사용자 입력을 embedding 공간에서 비교해 가장 가까운 route를 선택한다.
- routing decision 자체는 LLM generation보다 훨씬 싸고 빠르게 만들 수 있다.

README 기준 특징:

- `Route` 객체에 route 이름과 utterance 예시를 정의한다.
- `SemanticRouter` 또는 route layer가 입력 query를 route 이름으로 분류한다.
- OpenAI, Cohere, Hugging Face, FastEmbed encoder 등을 지원한다.
- Pinecone, Qdrant 등 vector store와 통합 가능하다.
- local 실행 옵션도 있으며, dynamic routes, LangChain integration, route optimization, multi-modal routes 문서를 제공한다.

쓰임새:

| 사용처 | 예 |
|---|---|
| intent routing | billing, support, coding, policy 질문 분기 |
| tool selection | 관련 없는 tool schema를 prompt에 넣지 않음 |
| prompt selection | chitchat, RAG, SQL, code-review prompt 분기 |
| safety prefilter | 금지 주제, 민감 주제, escalation 대상 분류 |

주의할 점:

- route 예문 품질이 성능을 크게 좌우한다.
- route가 많아지면 threshold 튜닝과 충돌 검사가 필요하다.
- embedding 기반 분류는 "의미적으로 비슷한데 정책상 다른" 요청을 헷갈릴 수 있다. 운영에서는 fallback route와 human review 기준이 필요하다.

### 3-3. vLLM Semantic Router

**정체**: vLLM 생태계의 system-level intelligent router. 모델이 많아지는 환경에서 비용, 지연, 안전, privacy, modality, reasoning 필요성을 기준으로 요청을 라우팅한다.

GitHub README와 Red Hat Developer 글 기준 핵심 가치:

- token economics: 낭비 token을 줄이고 token당 가치를 높임.
- LLM safety: jailbreak, sensitive leakage, hallucination 탐지.
- cloud, data center, edge에 걸친 model coordination.
- Rust/Candle 기반 저지연 classifier.
- Kubernetes/Envoy `ext_proc` 통합 방향.
- prompt guard, PII detection 같은 safeguard 내장.

Red Hat Developer 글은 reasoning-aware routing을 강조한다.

- 단순 요청은 작은/빠른 모델로 보낸다.
- reasoning이 필요한 요청은 더 강한 모델로 보낸다.
- 공개된 benchmark 설명에서는 MMLU-Pro/Qwen3 30B 조합에서 auto reasoning mode 조정으로 정확도 +10.2%, latency -47.1%, token usage -48.5% 결과를 제시한다.

관련 논문 흐름:

- `When to Reason`: reasoning mode가 필요한 query만 선별해 latency와 token을 줄이는 방향.
- `Signal Driven Decision Routing`: keyword, language, context length, auth, classifier, modality, grounding 등 여러 signal을 Boolean decision rule로 조합하는 구조.
- `Workload-Router-Pool`: workload, router, pool을 함께 최적화하는 vLLM Semantic Router 비전.
- `98x Faster LLM Routing`: router가 inference GPU를 잠식하지 않도록 prompt compression, Flash Attention, near-streaming 최적화 제시.

RouteLLM과의 차이:

| 항목 | RouteLLM | vLLM Semantic Router |
|---|---|---|
| 기본 문제 | strong/weak 모델 선택으로 비용 절감 | system-level policy routing |
| 주요 입력 | prompt difficulty / preference-based score | signal, classifier, safety, modality, auth, context |
| 배치 위치 | Python SDK 또는 OpenAI-compatible server | Envoy/ext_proc, gateway, vLLM serving 앞단 |
| 강점 | router 연구·평가, threshold calibration | cloud-native, safety/privacy, heterogeneous backend |
| 보완 필요 | gateway 운영 기능 | route policy 설계와 운영 복잡도 관리 |

### 3-4. Red Hat ET semantic_router

Red Hat ET의 `semantic_router` 저장소는 2025-08-30에 archive되었고 새 위치로 이동 안내가 있다. 현재 기준으로는 역사적 맥락과 설계 아이디어 참고용으로 보는 편이 맞다.

README에 남아 있는 주요 개념:

- Mixture-of-Models router.
- BERT classification으로 request intent를 보고 모델 선택.
- tool auto-selection.
- PII detection.
- prompt guard.
- semantic caching.
- Envoy proxy와 ExtProc gRPC server 구조.

즉, 현재는 `redhat-et/semantic_router` 자체보다 `vllm-project/semantic-router` 쪽을 기준으로 봐야 한다.

### 3-5. LangGraph

**정체**: long-running, stateful agent를 만들기 위한 low-level orchestration framework/runtime.

공식 문서 기준 핵심:

- LangGraph는 agent orchestration에 집중한 저수준 runtime이다.
- LangChain 없이도 사용할 수 있지만, model/tool integration에는 LangChain component를 자주 쓴다.
- durable execution, streaming, human-in-the-loop, persistence가 중심 기능이다.
- short-term working memory와 long-term memory를 포함한 stateful agent 구성이 가능하다.
- LangSmith와 연결하면 tracing, evaluation, deployment까지 이어진다.

LangChain과의 차이:

| 항목 | LangChain | LangGraph |
|---|---|---|
| 추상화 수준 | 높음 | 낮음 |
| 주 역할 | 모델, tool, agent loop 구성 편의 API | 상태ful graph runtime |
| 적합한 작업 | 빠른 prototype, 표준 agent loop | 복잡한 업무 흐름, 재개/승인/분기/상태 관리 |
| 운영 관점 | 간단하지만 내부 흐름이 추상화될 수 있음 | 명시적 graph라 디버깅과 제어가 쉬움 |

LangGraph를 쓰기 좋은 상황:

- 장시간 실행되거나 중간 실패 후 재개가 필요한 agent.
- 사람이 중간 승인해야 하는 workflow.
- agent 상태를 inspect/modify해야 하는 운영 절차.
- RAG, tool call, verifier, fallback, router 호출이 여러 단계로 엮이는 경우.
- 운영 trace를 보고 어느 node에서 실패했는지 추적해야 하는 경우.

단순한 `prompt -> LLM -> answer` 수준이면 LangGraph는 과하다. 하지만 "업무 절차"가 들어가기 시작하면 LangGraph의 명시적 상태 그래프가 장점이 된다.

## 4. 아키텍처 패턴

### 4-1. 비용 절감형 2단 모델 라우팅

```text
[App]
  |
  v
[RouteLLM]
  |-- easy / low-risk --> small model
  |-- hard / high-risk -> strong model
  |
  v
[Response + routing metadata]
```

적합:

- 고객지원 FAQ, 일반 Q&A, 코드 설명처럼 쉬운 요청 비율이 높은 서비스.
- 강한 모델 호출 비율을 통제해야 하는 SaaS.
- "비용을 줄이되 품질 저하는 허용하기 어렵다"는 요구.

필수 운영 장치:

- 실제 traffic 샘플 기반 threshold calibration.
- strong model 비율, fallback 비율, 사용자 불만족률 대시보드.
- weak model 응답이 낮은 confidence일 때 verifier 또는 strong model 재시도.

### 4-2. Intent 기반 tool/prompt routing

```text
[User prompt]
  |
  v
[Semantic Router]
  |-- route=support -> support RAG
  |-- route=billing -> billing workflow
  |-- route=code    -> code assistant prompt
  |-- route=unsafe  -> refusal / human review
  |
  v
[Selected chain/tool/model]
```

적합:

- tool schema가 많아 prompt token 비용이 커지는 agent.
- 부서별/업무별 RAG index가 나뉜 서비스.
- LLM이 tool 선택을 자주 틀리는 경우.

필수 운영 장치:

- route별 대표 utterance 관리.
- threshold와 unknown route 처리.
- route collision test set.
- route 변경 시 regression eval.

### 4-3. Reasoning budget routing

```text
[Request]
  |
  v
[Reasoning classifier]
  |-- simple   -> non-reasoning / short output model
  |-- complex  -> reasoning model or reasoning mode
  |
  v
[Answer]
```

적합:

- reasoning model의 token 폭증이 비용 문제를 만드는 경우.
- 모든 질문에 chain-of-thought/reasoning mode를 켜기엔 latency가 너무 큰 경우.
- vLLM 기반 자체 serving에서 policy를 gateway에 넣고 싶은 경우.

주의:

- "쉬운 요청" 오분류는 품질 손상으로 바로 이어진다.
- classifier 자체 latency가 작아야 한다.
- reason/non-reason decision 결과를 trace에 남겨야 나중에 품질 문제를 분석할 수 있다.

### 4-4. Stateful agent orchestration + router 결합

```text
[LangGraph]
  |
  |-- node: classify task
  |-- node: retrieve context
  |-- node: call model through router
  |-- node: verify answer
  |-- node: ask human if risky
  |-- node: final response
  |
  v
[Trace / Eval / Replay]
```

적합:

- 단발 답변보다 "업무 수행"이 목적일 때.
- 실패한 단계부터 재개해야 할 때.
- routing decision과 tool call을 모두 audit해야 할 때.

## 5. 관찰성은 선택사항이 아니다

LLM agent는 non-deterministic하다. 같은 prompt라도 model version, tool result, retrieval result, temperature, prompt template 변경에 따라 행동이 달라진다. 운영에서 필요한 것은 단순 로그가 아니라 **span 기반 trace**다.

MLflow 글 기준 2026년 LLM observability에서 봐야 할 항목:

- LLM call, tool invocation, retrieval, internal reasoning step을 span hierarchy로 남길 것.
- trace-level replay가 가능할 것.
- prompt versioning과 A/B test가 가능할 것.
- token cost, latency breakdown, circuit breaker를 볼 수 있을 것.
- OpenTelemetry 기반 SDK가 있으면 장기 유지보수에 유리하다.

도구 선택 감각:

| 도구 | 강점 | 맞는 상황 |
|---|---|---|
| MLflow | tracing, eval, prompt, AI gateway를 한 플랫폼에서 다룸 | 기존 ML/MLOps와 GenAI 운영을 같이 묶고 싶을 때 |
| LangSmith | LangChain/LangGraph 생태계와 밀착 | LangGraph 중심 개발팀 |
| Arize Phoenix | RAG debugging, retrieval relevance, document attribution | 검색 품질 문제가 많은 RAG |
| Langfuse | self-hosted analytics, data residency | 외부 SaaS trace 전송이 부담될 때 |
| Helicone | proxy 방식 API monitoring | 빠른 도입, 기본 cost/latency/logging |
| AgentOps | autonomous/multi-agent session 추적 | CrewAI/AutoGen류 agent session 관찰 |

운영 기준:

- router decision은 반드시 trace attribute로 남긴다.
- `selected_model`, `router_name`, `route`, `threshold`, `confidence`, `fallback_reason`, `token_cost`, `latency_ms`를 남긴다.
- eval은 offline benchmark만 믿지 말고 production sample 기반 golden set을 만든다.
- route/prompt/model 변경은 CI에서 regression eval을 통과해야 한다.

## 6. 로컬·오픈 모델과의 연결

사용자가 모은 local LLM 자료의 실무적 의미는 "router 뒤에 어떤 model pool을 둘 것인가"다.

Hardware별 model pool 예시:

| 환경 | 후보 | 역할 |
|---|---|---|
| CPU/16GB laptop | Phi-mini, Gemma small, Qwen small | 개발·테스트, route logic 검증 |
| 24GB VRAM | Qwen 30B급, Gemma 27B급, Devstral급 | coding/RAG/agent local backend |
| 48GB+ VRAM | Qwen 32B, Mistral Small급 | 내부 도구, private assistant |
| 80GB GPU/H100급 | 대형 reasoning/open-weight model | private cloud inference |
| multi-GPU | MoE 대형 모델, long-context model | enterprise workload |

중요한 원칙:

- 가장 큰 모델부터 시작하지 않는다. hardware에 안정적으로 맞는 모델이 운영상 더 낫다.
- RAG는 모델 크기보다 retrieval 품질, chunking, embedding 품질이 더 큰 병목일 수 있다.
- commercial use는 license 확인이 필수다. "open weight"와 "OSI open source"는 다르다.
- local model을 router pool에 넣으려면 OpenAI-compatible endpoint로 표준화하는 것이 편하다. Ollama, vLLM, SGLang, llama.cpp server, LiteLLM을 조합할 수 있다.

## 7. 선택 기준

### 7-1. 어떤 도구를 먼저 볼까?

| 목적 | 1차 후보 | 이유 |
|---|---|---|
| 강한 모델 호출 비용 절감 | RouteLLM | strong/weak routing에 특화 |
| intent/tool/prompt 분기 | Aurelio Semantic Router | LLM 호출 전 빠른 semantic route |
| vLLM 기반 inference gateway | vLLM Semantic Router | Envoy/K8s/safety/reasoning routing 방향 |
| 복잡한 agent workflow | LangGraph | durable execution, state, human-in-the-loop |
| multi-provider gateway | LiteLLM, Portkey | provider 표준화, fallback, budget, logging |
| RAG 품질 디버깅 | Phoenix, MLflow, LangSmith | retrieval trace와 eval |
| data residency 중시 관찰성 | Langfuse, MLflow self-host | self-host 가능 |

### 7-2. RouteLLM vs Semantic Router

| 질문 | RouteLLM | Semantic Router |
|---|---|---|
| "쉬운 질문은 싼 모델, 어려운 질문은 비싼 모델"인가? | 좋음 | 가능하지만 주 목적은 아님 |
| "billing 질문은 billing workflow, coding 질문은 coding tool"인가? | 부적합 | 좋음 |
| 학습된 router와 benchmark 평가가 필요한가? | 좋음 | route optimization은 가능하나 성격 다름 |
| LLM 호출 전에 빠르게 intent를 정하고 싶은가? | 일부 가능 | 좋음 |
| K8s/Envoy/gateway 레벨 policy가 필요한가? | 별도 구현 필요 | vLLM Semantic Router 쪽이 적합 |

### 7-3. LangGraph를 언제 붙이나?

LangGraph는 router의 대체재가 아니다. router를 호출하는 상위 workflow runtime으로 보는 게 맞다.

LangGraph가 필요한 신호:

- workflow 단계가 3개 이상이다.
- 중간 상태를 저장해야 한다.
- 사람이 approve/reject해야 한다.
- tool call 실패 후 재시도/우회가 필요하다.
- 어느 단계에서 어떤 모델/도구가 선택됐는지 trace해야 한다.
- "이 agent가 왜 이렇게 행동했나"를 나중에 재현해야 한다.

## 8. 추천 PoC 순서

### Phase 1. 단일 workflow + trace

목표:

- LangGraph로 간단한 RAG 또는 tool-calling workflow 1개 구성.
- 모든 node에 trace id를 붙인다.
- LangSmith 또는 MLflow 중 하나로 span을 본다.

성공 기준:

- 각 단계 input/output이 trace에서 보인다.
- 실패 node를 식별할 수 있다.
- prompt version과 model version을 기록한다.

### Phase 2. intent route 추가

목표:

- Aurelio Semantic Router로 3~5개 route를 만든다.
- route별 prompt/tool/RAG index를 분리한다.

성공 기준:

- unknown route 처리 기준이 있다.
- route별 test utterance set이 있다.
- route 오분류를 수집할 수 있다.

### Phase 3. cost routing 추가

목표:

- RouteLLM 또는 단순 heuristic router로 strong/weak model split을 만든다.
- 1~2주 production-like sample로 threshold를 보정한다.

성공 기준:

- strong model 호출 비율을 통제할 수 있다.
- weak model route의 품질 저하율을 측정한다.
- fallback 또는 verifier 기준이 있다.

### Phase 4. serving/gateway로 승격

목표:

- vLLM 또는 OpenAI-compatible endpoint 뒤에 router/gateway 배치.
- fallback, retry, budget, auth, audit를 설계한다.

성공 기준:

- router decision이 audit 가능하다.
- 장애 시 fallback이 동작한다.
- 비용·latency·품질 대시보드가 한 화면에 있다.
