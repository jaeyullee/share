## 분산 워크로드 스택 전제 (RHOAI 3.4)

```
Notebook + CodeFlare SDK        ← 입구: Python으로 RayCluster CRD + Kueue 제출
        │
        ▼
Ray (KubeRay) / Kubeflow Trainer ← 실행 엔진: "무엇을·얼마나" 정의, Pod 생성 주체
        │
        ▼
Kueue                            ← 논리적 쿼터 관제: admit/대기 판정 (Pod은 안 띄움)
        │
        ▼
kube-scheduler → kubelet         ← 물리적 노드 배치 + 실제 컨테이너 기동
```

- **Kueue = 관제/승인/쿼터(gatekeeper)** 까지만. 실제 Pod 생성은 **오퍼레이터(Ray/Trainer)**, 노드 배치는 **kube-scheduler**, 기동은 **kubelet**.
- 모든 요청의 단일 창구는 **kube-apiserver**.

## 이슈 #1 — 쿼터 ≠ 노드 실상: 부분 스케줄링 데드락 ⭐

가장 중요. 분산학습에서 실무적으로 가장 골치 아픈 함정.

### 근본 원인: Kueue는 노드를 보지 않는다

Kueue의 자원 판단은 **물리 노드 상태가 아니라 관리자가 설정한 논리적 쿼터 장부**다.

```
가용 = nominalQuota(관리자 설정값) − Σ(이미 admit된 워크로드 점유분)
```

- Kueue가 watch하는 것: `ClusterQueue`/`LocalQueue`/`ResourceFlavor`(쿼터 한도) + `Workload`(승인 이력).
- **`Node`의 allocatable은 보지 않음.** → 쿼터를 실제 클러스터 용량보다 크게 잡으면(over-provisioning), 노드에 자리가 없어도 Kueue는 "쿼터 남음 → admit".

### 증상 1: Pending

```
쿼터상 GPU 여유 있음 → Kueue admit → 오퍼레이터가 Pod 생성 요청
        → kube-scheduler가 노드 보니 자리 없음 → Pod Pending
```

### 증상 2: 부분 스케줄링 데드락 (더 위험)

Kueue는 **admission 레벨에선 all-or-nothing(갱 스케줄링)** 을 보장하지만, **일단 admit된 뒤 kube-scheduler의 Pod 단위 배치에서는 갱 보장이 자동으로 안 이어진다.**

```
worker 4개 Ray 잡 → Kueue admit
        ▼
kube-scheduler는 Pod을 "하나씩" 스케줄링
        ▼
worker 2개만 노드에 들어가고 2개는 Pending
        ▼
들어간 2개가 GPU를 "잡은 채" 나머지를 무한정 대기  ← 자원 점유 + 진행 불가 (데드락)
```

→ 일부만 떠서 **비싼 GPU를 물고 늘어지며** 전체 잡은 진행 못 함. 여러 잡이 서로 이 상태면 클러스터 전체 교착.

### 방어선

| 순위 | 방어 | 내용 |
|---|---|---|
| 1차 | **쿼터를 물리 용량에 정렬** | `nominalQuota`를 실제 GPU/노드 수에 맞게 설정. over-provisioning 금지 |
| 2차 | **스케줄러 레벨 갱 스케줄링** | scheduler-plugins **Coscheduling** 또는 Kueue 연동 기능으로 "worker 전부 들어갈 때만 배치" 강제 |
| 3차 | 모니터링 | `Pending` 장기 체류 Pod / admit됐는데 Running 못 가는 Workload 알람 |

> 핵심 한 줄: **Kueue 통과 ≠ 노드 배치 보장.** 판정이 2단계(논리 쿼터 → 물리 노드)이고, 그 사이 갭이 데드락의 씨앗.

## 이슈 #2 — Eviction은 over-provisioning만으론 안 난다 (오해 주의)

"쿼터가 노드보다 많으니 돌던 Pod이 쫓겨나겠네"는 **틀린 모델.** 자리 없음의 기본 결과는 `Pending`이지 eviction이 아니다. Eviction은 **별도 트리거**가 있어야 발생한다.

| Eviction 트리거 | 주체 | 조건 |
|---|---|---|
| **우선순위 선점(preemption)** | kube-scheduler | 새 Pod이 더 높은 `PriorityClass` → 낮은 Pod 축출하고 자리 확보 |
| **노드 압박(node pressure)** | kubelet | 노드 메모리/디스크 부족 → Pod 강제 축출 |
| **Kueue 선점** | Kueue | 더 높은 우선순위 워크로드 위해 쿼터 회수 → 기존 워크로드 통째 evict |

→ 딜리버리 시사점: **장기 학습 잡에 함부로 높은 우선순위 클래스를 섞으면**, 선점으로 멀쩡히 돌던 잡이 통째로 죽고 체크포인트 없으면 처음부터 재시작. 우선순위 정책은 신중하게.

## 이슈 #3 — Kueue ↔ Time-slicing 혼동

별개 층위인데 "둘 다 GPU 나눠 쓰는 것" 으로 뭉뚱그리면 설계가 어긋남.

| | 무엇을 | 층위 |
|---|---|---|
| **Time-slicing** | GPU 1장을 N개 리소스로 **쪼개 노출**(공급↑) | 디바이스/드라이버 |
| **Kueue** | 잡이 **언제 입장**할지 줄 세움(수요 배분) | 스케줄/배치 |

- 보완 관계: **TS = 공급(분할) 늘리기 / Kueue = 수요(배분) 줄 세우기.**
- TS로 오버커밋한 GPU 위에 Kueue로 오버서브스크립션을 관리하면 유휴 많은 노트북·배치 활용률↑. 단 **이슈 #1의 데드락 위험은 TS 환경에서 더 심해짐**(논리 슬롯 N개가 물리 1장이라 쿼터-실상 괴리 확대).
- 상세: [[GPU-공유전략-MIG-MPS-Timeslicing]] §"Time-slicing ≠ Kueue".
