# GPU 공유 전략 — MIG / MPS / Time-slicing

> 비싼 GPU 1장을 여러 소비자(파드·프로세스·VM)가 어떻게 나눠 쓸지의 문제.
> 세 방법은 경쟁 관계가 아니라 **격리 강도 ↔ 집적도(활용률) 트레이드오프 스펙트럼**이며, 실무에선 계층으로 쌓아 쓴다.

---

## 세 메커니즘 비교

| 메커니즘 | 분할 축 | 격리 강도 | 메모리 보호 | 장애 격리 | 오버커밋 | GPU Operator 광고 |
|---|---|---|---|---|---|---|
| **MIG** | 공간(SM+메모리 **물리** 분할) | **강** | ✅ 전용·하드웨어 | ✅ fault 격리 | ❌ 고정 | `nvidia.com/mig-1g.5gb` |
| **MPS** | 공간(단일 CUDA 컨텍스트, SM % 동시 배분) | 중 | ⚠️ 부분(Volta+) | ❌ 전파 위험 | 제한적 | `nvidia.com/gpu` (replicas) |
| **Time-slicing** | **시간**(스케줄러 번갈아) | 약/없음 | ❌ | ❌ | ✅ N배 광고 | `nvidia.com/gpu` (replicas) |

```
강한 격리·결정론          ←——————————————→          높은 집적·유휴흡수
   MIG                         MPS                    Time-slicing
(경합 사전 차단·분할)      (동시 공간 공유)          (경합 시간분할)
```

- **MIG** = 하드웨어가 구역을 펜싱. 결정론적·SLA 보장. 고정 크기, 오버커밋 불가. "경합 해결"보다 **격리·SLA 보장** 동기.
- **MPS** = 여러 프로세스를 **한 CUDA 컨텍스트로 합쳐** SM을 비율로 **동시** 사용. 컨텍스트 스위칭 없어 지연 적음. 주소공간 공유 → OOM/크래시 전파 가능.
- **Time-slicing** = 정원만큼 입장시켜 **번갈아** 태움. 격리·메모리보호 전혀 없음. 유휴 많은 워크로드 집적에 최강.

---

## SM = 세 방법을 꿰는 축

**SM(Streaming Multiprocessor)** = GPU의 연산 기본 블록. GPU는 SM을 수십~수백 개 박은 칩(A100=108, H100 SXM=132). SM 하나 = CUDA 코어 + 텐서 코어 + 워프 스케줄러 + 레지스터 + shared memory/L1. GPU는 일(스레드 블록)을 **SM 단위로** 던져 돌린다. MIG의 "컴퓨트 슬라이스"가 곧 SM 묶음(A100 7슬라이스 = 108 SM을 7덩이로).

```
물리: SM ▪▪▪▪▪▪▪▪▪▪▪▪▪▪  (총 108개)

MIG          ▪▪▪▪│▪▪▪▪│▪▪▪▪│▪▪▪▪   ← SM을 물리로 갈라 전용 배정 (벽 있음)
Time-slicing ▪▪▪▪▪▪▪▪▪▪▪▪▪▪ × 차례   ← 전부 다 쓰되 시간으로 번갈아
MPS          A:▪▪▪▪ B:▪▪▪▪▪▪▪▪▪▪    ← 같은 순간 SM을 비율로 동시 나눔 (벽 없음)
```

| | SM(컴퓨트) | 같은 순간 동시? | 경계 |
|---|---|---|---|
| **MIG** | 물리적으로 갈라 전용 | ✅(각자 자기 SM) | 하드웨어 벽 |
| **Time-slicing** | 전체를 번갈아 | ❌(한 번에 1명) | 없음, 시간으로 분리 |
| **MPS** | 비율로 동시 배분 | ✅(여럿이 동시) | 소프트(스케줄 레벨) |

> **MPS의 "SM 나눔"** = active thread percentage(클라이언트당 동시 사용 SM 비율 상한)로 **동시에 쓰되 각자 쓸 수 있는 SM 양을 제한**하는 것. MIG처럼 "이 SM은 네 전용"이 아니라 **소프트 상한**이며 컨텍스트 스위칭 없이 진짜 병렬.

---

## 컴퓨트 vs VRAM — time-slicing에서 완전히 다르게 동작

핵심: **시간 분할되는 건 컴퓨트(실행)뿐, VRAM은 번갈아 쓰지 않는다.**

```
컴퓨트(SM)  →  번갈아 (time-multiplex)   : 한 순간 1명, 차례 끝나면 다음
VRAM(HBM)   →  안 번갈아 (동시 상주)      : 모든 프로세스 데이터가 동시에 메모리에 그대로
```

- 메모리는 점유형 리소스라 시간 분할 불가 → **각 프로세스 할당을 HBM에 동시 상주**시키고 **용량(공간)으로 나눠 가짐.**
- 기본적으로 **한도 강제 없음** → 합산 할당이 GPU 메모리 넘으면 그냥 **OOM.** (= time-slicing이 메모리 격리를 못 하는 진짜 이유)
- MIG가 메모리 슬라이스까지 물리로 가르는 이유 = 메모리는 시간분할이 불가능하니 **공간으로 못 박아야** 격리가 됨.

### 컨텍스트 스위칭이 실제로 교체하는 것 = "실행 상태"(소량)

| 스위칭 시 교체 | 위치 | 크기 |
|---|---|---|
| 레지스터 파일, 워프/스케줄러 상태, shared memory/L1, PC, 채널 상태 | 온칩(SM 내부)·예약영역 | 작음, 빠름 |
| 모델 가중치·KV·텐서(전역 메모리) | **HBM에 그대로 상주** | 안 건드림 |

> 대용량 VRAM 데이터는 옮기지 않는다(매 스위칭마다 수십 GB 복사 불가). 흔히 떠올리는 "스왑메모리에 잠깐 저장"은 **CUDA Unified Memory(UVM)** 라는 **별도 opt-in 기능**(HBM↔호스트 RAM 페이지 마이그레이션)이고, PCIe 왕복이라 매우 느려 추론 서빙엔 거의 안 씀. **기본 time-slicing은 스왑 안 함.**

### 세 방법의 SM·VRAM 격리 정리

| | SM(컴퓨트) | VRAM | 메모리 대역폭·L2 | 격리 |
|---|---|---|---|---|
| **MIG** | 전용 물리 분할 | **전용 물리 분할** | **전용** | 강 (둘 다 벽) |
| **MPS** | 비율 동시 공유(소프트) | 공유 풀(소프트 한도) | 공유 | 중 |
| **Time-slicing** | 시분할 번갈아 | 공유 풀(한도 없음) | 공유 | 약 |

> VRAM은 셋 다 "각자 점유"가 맞지만, **그 점유에 벽이 있느냐(MIG) 없느냐(MPS/TS)** 가 격리 강도를 가른다.

## 두 층위의 공유 — 파드 간 vs 컨테이너 안

공유는 별개의 두 층위에서 동시에 일어난다.

| 층위 | 무엇을 나누나 | 수단 |
|---|---|---|
| **파드 간**(K8s 경계) | GPU를 여러 컨테이너에 배분 | device plugin의 `mig`/`timeSlicing`/`mps` 전략 |
| **컨테이너 안**(프로세스 경계) | 할당받은 GPU를 여러 ps가 공유 | 기본 컨텍스트 스위칭, 또는 MPS |

- 컨테이너는 프로세스 네임스페이스일 뿐 → 그 안에서 프로세스 여러 개가 마운트된 GPU(풀 GPU/MIG 슬라이스/TS 레플리카)를 같이 봄.
- 컨테이너 안 멀티프로세스 GPU 공유 = **MPS의 원래 태생 용도**(MPI 랭크 동시 실행).
- vLLM 서빙은 보통 **컨테이너당 1개 모델 프로세스**로 둠(OOM 전파·메모리 보호 때문). 컨테이너 내 멀티프로세스 공유가 빛나는 건 HPC/배치·멀티랭크 학습이나 신뢰 도메인 같은 경량 추론 다수.

## 복합 사용 = 계층으로 쌓기

"고객사가 복합적으로 쓴다"는 건 보통 이 레이어링:

```
물리 GPU (예: A100 80GB)
   └─ MIG로 물리 분할          ← 1차: 강한 격리·SLA 경계 (테넌트/프로덕션 단위)
       └─ 각 슬라이스를 MPS 또는 time-slicing으로 재공유  ← 2차: 슬라이스 안에서 집적
```

- **MIG → time-slicing**: 1g.5gb 슬라이스를 다시 N개로 광고. 유휴 많고 격리만 필요한 워크로드(노트북/실험)를 슬라이스 안에 집적.
- **MIG → MPS**: 슬라이스 안에서 신뢰 도메인 같은 경량 프로세스 동시 실행.
- MPS와 time-slicing은 보통 같은 디바이스에 동시에 쌓지 않음(둘 다 2차 레이어 자리 경쟁).
- 역할 분담: **MIG = 테넌트/SLA 경계**, **MPS·time-slicing = 그 경계 안에서의 집적 수단.**

## 정책 판단 프레임 — 어디에 뭘 쓸까

판단 축 4개: **격리 요구 · SLA 민감도 · 신뢰 도메인 · 유휴율.**

| 워크로드 | 격리 | SLA | 권장 | 이유 |
|---|---|---|---|---|
| **프로덕션 서빙(멀티테넌트)** | 강 | 빡셈 | **MIG 전용** | 결정론적 지연·장애 격리, 이웃 간섭 0 |
| **고객사 A/B 테넌트 분리** | 강 | 중 | **MIG** | 메모리·fault 하드웨어 경계 = 보안/과금 경계 |
| **개발자 노트북·실험(버스티, 유휴↑)** | 약 | 느슨 | **Time-slicing**(또는 MIG슬라이스+TS) | 집적도 최대, 지터 감수 |
| **같은 팀 경량 동종 프로세스 다수** | 중 | 중 | **MPS** | 컨텍스트 스위칭 지연 회피, 신뢰 동일 |
| **소형 모델 다수 격리 서빙** | 중~강 | 중 | **MIG 1g 여러 개** | 모델 간 간섭·OOM 전파 차단 |

**의사결정 규칙 (위→아래 우선):**
1. **메모리 보호/장애 격리 필수면 → MIG.** 멀티테넌트·프로덕션·과금경계는 무조건. (TS/MPS는 메모리 보호 없어 한 워크로드 OOM이 이웃을 죽임)
2. **SLA 빡세면 → time-slicing 금지.** 컨텍스트 스위칭이 TTFT/TPOT에 지터 주입. 결정론 필요하면 MIG.
3. **유휴율 높고 격리 약해도 되면 → time-slicing**으로 N배 오버커밋해 집적도 극대화.
4. **신뢰 도메인 같고 SM 미세 분배로 동시성만 올리려면 → MPS.**

## 자주 빠지는 함정

- **time-slicing을 프로덕션 서빙에 사용**: 메모리 보호 없어 한 파드 OOM이 같은 GPU 전체를 끌어내림. 데모는 잘 돌다 부하 들어가면 터짐.
- **MPS의 "부분 격리"를 완전 격리로 오해**: Volta+가 주소공간은 나눠도 치명적 fault는 여전히 전파 가능. 신뢰 경계로 쓰면 안 됨.
- **MIG 밀도만 보고 호스트 CPU 누락**: 슬라이스를 또 time-slice하면 파드가 더 늘어 `Σ(2+N)` CPU 폭증 (→ `../0-Important/03-RHOAI-워커노드-리소스-산정법` 참조).
- **노드 안에서 전략 혼용**: GPU Operator의 `sharing` 전략(`mig`/`timeSlicing`/`mps`)은 노드 라벨/ClusterPolicy로 거는데, 한 노드에 섞으려면 **노드풀을 전략별로 분리**하는 게 깔끔.

## Time-slicing ≠ Kueue (헷갈림 주의)

| | 무엇을 하나 | 층위 |
|---|---|---|
| **Time-slicing** | GPU 1장을 N개 리소스로 **쪼개 노출** | 디바이스(하드웨어/드라이버) |
| **Kueue** | 어떤 잡이 **언제 입장**할지 쿼터·우선순위로 **줄 세움** | 스케줄/배치 |

- **Time-slicing의 실제 분할**은 NVIDIA device plugin/GPU Operator가 함(`replicas: N` 정적 설정 + 하드웨어 컨텍스트 스위칭). Kueue 무관.
- **Kueue**는 ClusterQueue/LocalQueue 쿼터, gang scheduling, 선점, 쿼터 빌려쓰기로 **잡을 줄 세움.** GPU를 직접 안 쪼갬.
- 보완 관계: **time-slicing = 공급(분할) 늘리기**, **Kueue = 수요(배분) 줄 세우기.** 유휴 많은 노트북·배치를 TS GPU 위에 Kueue로 오버서브스크립션 관리하면 활용률↑. (OpenShift AI도 분산 워크로드/배치에 Kueue 채택)

### Time-slicing의 "사전 정원" 성격

- 설정은 **정적**: `replicas: N`을 미리 박아 물리 GPU 1장을 `nvidia.com/gpu` N개로 고정 광고. 요청마다 동적 재단 아님.
- 단 자르는 건 **자원이 아니라 정원(오버커밋 배수).** MIG는 슬롯=실제 SM+메모리 구역이지만, TS 슬롯 N개는 **같은 풀 GPU 입장권 N장.**
- 런타임 시간 배분은 **균등 라운드로빈**(요청 내용·크기 무관, QoS/가중치 없음 — 기본값).

| | 미리 자르나 | 자르는 대상 | 런타임 배분 |
|---|---|---|---|
| **MIG** | ✅ 자원 진짜 분할 | SM+메모리 물리 구역 | 없음(전용 고정) |
| **Time-slicing** | ✅ 개수만 고정 | 정원(오버커밋 배수) | 균등 라운드로빈 |
| **MPS** | ✅ 클라이언트당 SM% 상한 설정 가능 | SM 비율(소프트) | 동시 공간 공유 |
