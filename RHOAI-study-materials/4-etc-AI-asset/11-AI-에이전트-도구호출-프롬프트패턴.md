> OCP 엔지니어 관점 | 2026-04-10 | 예상 읽기 시간: 10분

---

## 1. 에이전트란 무엇인가

LLM은 기본적으로 "질문 하나 받고 답 하나 내놓는" 구조다. 에이전트는 다르다.

> **에이전트 = LLM + 도구 + 루프**

에이전트는 목표를 받으면 스스로 판단해서 도구를 호출하고, 결과를 보고 다음 행동을 결정한다. 이 루프를 목표가 달성될 때까지 반복한다.

### OCP 비유

> OCP의 Operator와 같다. Operator는 원하는 상태(desired state)를 보고, 현재 상태와 비교해서, 필요한 조치를 취하고, 다시 확인한다. 에이전트도 마찬가지다. 목표 상태를 향해 스스로 행동하고 확인한다.

## 2. 도구 호출(Tool Calling) 메커니즘

### 기본 흐름

```
1. 앱이 LLM에게 도구 정의를 전달
   (도구 이름, 파라미터, 설명)

2. LLM이 응답 생성 중 도구가 필요하다고 판단하면
   tool_calls 필드에 호출 요청을 담아 반환

3. 앱이 실제 도구 함수를 실행

4. 결과를 role="tool" 메시지로 추가

5. 다시 LLM 호출 → 최종 답변 생성
```

### Llama Stack에서 도구 정의 예시 (Python)

```python
tools = [
    {
        "tool_name": "favorite_color_tool",
        "description": "도시의 대표 색상을 반환한다",
        "parameters": {
            "city": {"param_type": "str", "description": "도시 이름"},
            "country": {"param_type": "str", "description": "국가 이름"}
        }
    }
]

response = client.inference.chat_completion(
    model_id="meta-llama/Llama-3.1-8B-Instruct",
    messages=messages,
    tools=tools,
    tool_choice="auto"
)
```

### Completion API vs Agent API 비교

| 항목 | Completion API | Agent API |
|------|---------------|-----------|
| 도구 루프 관리 | 앱이 직접 | 프레임워크가 처리 |
| 메시지 히스토리 | 앱이 직접 관리 | 세션으로 자동 관리 |
| 코드 복잡도 | 높음 | 낮음 |
| 제어권 | 높음 | 낮음 |
| 양자화 모델 호환성 | 좋음 | 주의 필요 |
| 디버깅 용이성 | 쉬움 | 어려움 |

## 3. MCP (Model Context Protocol)

MCP는 LLM과 외부 도구를 연결하는 표준 프로토콜이다.

### OCP 비유

> OCP의 CRI(Container Runtime Interface)와 같다. CRI가 있어서 containerd든 CRI-O든 교체 가능하듯, MCP가 있어서 Claude든 Cursor든 같은 도구 서버를 재사용할 수 있다.

### MCP 통합 3가지 방식

```
방식 1: 로컬 인라인 도구
앱 코드 안에 도구 함수 직접 구현
→ 가장 단순, 제어권 최대

방식 2: 원격 MCP 서버 (SSE)
MCP 서버를 Llama Stack에 toolgroup으로 등록
→ 클라이언트 코드 단순, 원격 실행 적합

방식 3: 로컬 MCP 브리지 (stdio)
앱이 로컬에서 MCP 서버를 stdio로 실행
MCP tool schema를 Llama Stack 포맷으로 변환
→ 로컬 환경 접근이 필요할 때
```

### 원격 MCP 서버 등록 예시

```python
# supergateway로 stdio MCP를 SSE로 변환 후 등록
client.toolgroups.register(
    toolgroup_id="my-tools",
    provider_id="model-context-protocol",
    mcp_endpoint={"uri": "http://localhost:8002/sse"}
)

# 에이전트에 toolgroup 연결
agent = client.agents.create(
    agent_config={
        "model": "meta-llama/Llama-3.1-8B-Instruct",
        "toolgroups": ["my-tools"]
    }
)
```

## 4. Llama Stack 아키텍처

Llama Stack은 AI 애플리케이션을 위한 표준 API 계층이다.

```
[애플리케이션]
      ↓
[Llama Stack API]  ← 표준 인터페이스
      ↓
┌─────────────────────────────────┐
│  플러그인 레이어                  │
│  ├── 모델 서빙 (Ollama / vLLM)   │
│  ├── 벡터 DB (Chroma / Milvus)   │
│  ├── 도구 (MCP 서버들)            │
│  └── 가드레일 (Llama Guard)       │
└─────────────────────────────────┘
```

### 핵심 특징

- **표준 API + 여러 배포판**: 특정 구현체에 종속되지 않음
- **플러그인 방식**: 모델 서버, 벡터 DB, 도구를 교체 가능
- **RAG 내장**: `builtin::rag/knowledge_search` 도구 그룹 기본 제공
- **빠른 변화**: `/docs` 엔드포인트가 공식 문서보다 최신

### Llama Stack 주요 API

```python
# 모델 등록
client.models.register(model_id="...", provider_id="ollama")

# 벡터 DB 등록
client.vector_dbs.register(
    vector_db_id="my-kb",
    embedding_model="all-MiniLM-L6-v2",
    embedding_dimension=384
)

# 문서 적재
client.tool_runtime.rag_tool.insert(
    vector_db_id="my-kb",
    documents=[...],
    chunk_size_in_tokens=125
)

# 에이전트 생성
client.agents.create(agent_config={...})
```

## 5. 프롬프트 패턴 6종

LLM 응답 품질은 프롬프트 설계에 크게 좌우된다. 개발자가 자주 쓰는 패턴 6가지다.

### 패턴 1: 생성/코드 생성

```
"Python으로 파일 존재 여부를 확인하는 함수를 작성해줘.
Path 라이브러리를 사용하고, 파일이 없으면 FileNotFoundError를 발생시켜."
```

짧고 구체적으로. 언어, 라이브러리, 예외 처리 방식까지 명시한다.

### 패턴 2: 페르소나 패턴

```
"OpenShift 운영 엔지니어로서, 다음 Pod CrashLoopBackOff 로그를 분석해줘."
```

역할을 부여하면 해당 전문 영역에 맞는 관점으로 답한다.

### 패턴 3: 문제 해결

```
"다음 Go 코드에서 메모리 누수가 발생한다. 원인을 찾고 수정해줘.
[코드 붙여넣기]"
```

문제 상황과 코드를 함께 제공한다.

### 패턴 4: 개발 패턴 (긴 프로그램)

```
"Kubernetes Operator를 Go로 작성해줘.
- CRD: MyApp
- Reconcile 루프에서 Deployment 생성/업데이트
- Status 조건 업데이트 포함"
```

요구사항을 목록으로 명확히 나열한다. 결과는 반드시 검토해야 한다.

### 패턴 5: 재작성 (리라이팅)

```
"다음 Python 코드를 PEP 8 스타일 가이드에 맞게 리팩토링해줘.
타입 힌트 추가, 함수 분리, 독스트링 포함."
```

기준(스타일 가이드, 모범 사례)을 명시한다.

### 패턴 6: 강사 패턴

```
"다음 코드가 왜 비효율적인지 설명해줘.
어떻게 개선할 수 있는지 단계별로 알려줘."
```

설명과 학습을 요청할 때 쓴다.

### 프롬프트 작성 원칙

| 원칙 | 나쁜 예 | 좋은 예 |
|------|---------|---------|
| 구체적으로 | "코드 고쳐줘" | "Python 3.11, FastAPI로 JWT 인증 미들웨어 작성" |
| 컨텍스트 제공 | "왜 안 되지?" | "OCP 4.14, vLLM 0.4.2 환경에서 OOM 발생. 로그: [...]" |
| 출력 형식 지정 | "설명해줘" | "표로 정리해줘. 열: 항목, 설명, 예시" |
| 토큰 절약 | 긴 배경 설명 | 핵심만 압축해서 제공 |

## 6. Lola: AI 컨텍스트 패키지 관리자

### 문제 인식

스킬, MCP 서버, 에이전트 지침(AGENTS.md), 명령 파일 같은 AI 컨텍스트 자산이 늘어나고 있다. 이걸 어떻게 관리할까?

### OCP 비유

> Helm이 Kubernetes 리소스를 패키지로 관리하듯, Lola는 AI 컨텍스트 자산을 패키지로 관리한다.

### Lola 구조

```
[Lola Marketplace]  ← 모듈 카탈로그/레지스트리
        ↓
[Lola Module]       ← 배포 단위 (스킬 + MCP 서버 + 지침 묶음)
        ↓
[AI Assistant]      ← Claude Code, Cursor 등에 설치
```

### 기본 사용법

```bash
# 설치
uv tool install git+https://github.com/RedHatProductSecurity/lola

# 마켓플레이스 등록
lola market add <marketplace-url>

# 모듈 목록 조회
lola market ls

# 모듈 설치 (Claude Code에)
lola install claude-md-management

# 설치 목록 확인
lola list

# 제거
lola uninstall claude-md-management
```

### 핵심 가치

- **버전 관리**: AI 컨텍스트를 코드처럼 버전 관리
- **감사 가능성**: 어떤 스킬이 설치되어 있는지 추적
- **이식성**: 여러 AI 비서에 동일한 컨텍스트 배포
- **중앙 통제**: 조직 단위로 스킬/명령 표준화

## 7. 에이전트 보안 고려사항

에이전트는 도구를 자율적으로 호출하기 때문에 보안 위협이 다르다.

### 주요 위협

| 위협 | 설명 | 대응 |
|------|------|------|
| **프롬프트 인젝션** | 악의적 입력으로 에이전트 행동 조작 | 입력 검증, 가드레일 |
| **도구 남용** | 에이전트가 의도치 않은 도구 호출 | 도구 권한 최소화 |
| **컨텍스트 오염** | 악의적 문서가 RAG 결과에 포함 | 문서 소스 검증 |
| **과도한 자율성** | 에이전트가 너무 많은 권한 행사 | Human-in-the-loop |

### Llama Guard

Red Hat 엔터프라이즈 RAG 스택에는 Llama Guard가 포함된다. 모든 요청/응답이 가드레일을 거쳐 유해 출력을 차단한다.

```
사용자 → [Llama Guard 입력 검사] → LLM → [Llama Guard 출력 검사] → 응답
```

## 8. 핵심 원칙 정리

1. **에이전트는 Operator처럼 생각한다.** 목표 상태를 향해 루프를 돌며 도구를 호출한다.
2. **MCP는 도구의 CRI다.** 한 번 만든 MCP 서버를 여러 AI 비서에서 재사용한다.
3. **Completion API는 제어, Agent API는 편의.** 상황에 맞게 선택한다.
4. **프롬프트는 구체적일수록 좋다.** 언어, 버전, 출력 형식, 제약 조건을 명시한다.
5. **AI 출력은 초안이다.** 코드 생성 결과는 반드시 검토하고 테스트한다.
6. **AI 컨텍스트도 코드처럼 관리한다.** 스킬과 MCP 서버를 버전 관리하고 패키지로 배포한다.
