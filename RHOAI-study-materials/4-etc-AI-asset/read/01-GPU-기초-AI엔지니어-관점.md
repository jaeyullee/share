# GPU 기초: AI 엔지니어가 알아야 할 것들

> OCP 엔지니어 관점 10분 요약. GPU가 왜 AI에 필수인지, 어떻게 동작하는지, 어떤 프레임워크를 골라야 하는지.

---

## 1. GPU가 AI에 필수인 이유

**비유: 고속도로 vs 골목길**

CPU는 왕복 8차선 고속도로 위의 스포츠카 몇 대다. 빠르고 똑똑하지만 한 번에 처리하는 차량 수가 적다. GPU는 왕복 수천 차선 국도 위의 트럭 수만 대다. 한 대 한 대는 느리지만, 동시에 움직이는 물동량이 압도적이다.

AI 학습은 행렬 곱셈을 수십억 번 반복하는 작업이다. 이건 "빠른 차 몇 대"보다 "느려도 수만 대 동시"가 훨씬 유리하다.

| 항목 | CPU | GPU |
|------|-----|-----|
| 코어 수 | 수십 개 | 수천~수만 개 |
| 단일 스레드 성능 | 높음 | 낮음 |
| 병렬 처리 | 제한적 | 특화 |
| 적합한 작업 | 복잡한 제어 흐름 | 반복적 수치 연산 |
| AI 학습 속도 | 기준 | 수십~수백배 빠름 |

## 2. GPU 동작 구조: Grid / Block / Thread

**비유: 공장 라인**

GPU 프로그램은 공장 라인처럼 생겼다.

- **Grid**: 공장 전체
- **Block**: 공장 안의 작업 팀 (각 팀은 독립적으로 돌아감)
- **Thread**: 팀원 한 명 (같은 작업을 각자 다른 데이터에 수행)

```
GPU 실행 구조
┌─────────────────────────────────┐
│  Grid (전체 작업)                │
│  ┌──────────┐  ┌──────────┐    │
│  │  Block 0 │  │  Block 1 │    │
│  │ T0 T1 T2 │  │ T0 T1 T2 │   │
│  └──────────┘  └──────────┘    │
└─────────────────────────────────┘
```

GPU에서 실행되는 함수 단위를 **커널(Kernel)**이라고 부른다. 커널 하나가 수만 개 스레드에서 동시에 실행된다. NVIDIA A100 기준으로 SM(Stream Multiprocessor) 108개, SM당 2048 스레드, 총 22만 개 스레드를 동시에 처리할 수 있다.

**핵심 원칙: SIMD**

Single Instruction, Multiple Data. 하나의 명령을 여러 데이터에 동시 적용한다. 배열 100만 개를 각각 2배로 만드는 작업이라면, CPU는 순서대로 100만 번 실행하고 GPU는 100만 개를 동시에 실행한다.

## 3. GPU 알고리즘 사고법: 접두사 합 예시

**왜 알고리즘이 달라야 하나?**

CPU에서 자연스러운 코드가 GPU에서는 비효율적일 수 있다. 접두사 합(prefix sum)이 좋은 예다.

**CPU 방식 (O(N), 직렬)**
```
[1, 4, 7, 1, 3] → [1, 5, 12, 13, 16]
앞에서부터 하나씩 더한다.
```

**단순 GPU 병렬화 (겉보기만 병렬)**
```
각 스레드가 자기 인덱스까지 전부 더함 → 총 work가 O(N²)
오히려 CPU보다 느릴 수 있다.
```

**효율적인 GPU 방식 (O(N log N) work, O(log N) span)**

이진 트리처럼 윈도우를 2배씩 키우며 log N번 반복한다.

```
1단계: 각 원소가 바로 왼쪽 1개를 더함
2단계: 각 원소가 왼쪽 2개 범위를 더함
3단계: 각 원소가 왼쪽 4개 범위를 더함
...
```

**교훈**: GPU 알고리즘은 "총 연산량(Work)"보다 "병렬 깊이(Span)"를 줄이는 방향으로 설계한다. 총 work가 CPU보다 많아도 span이 작으면 GPU에서 더 빠르다.

퀵소트도 같은 원리다. 분할(partition) 단계를 GPU 커널로 처리하고, 두 하위 파티션을 동시에 재귀 정렬한다. 핵심 패턴은 **카운트 → 스캔(prefix sum) → 산란(scatter)** 3단계다.

## 4. GPU 프레임워크 선택 가이드

| 프레임워크 | 추상화 수준 | 장점 | 단점 | 추천 상황 |
|-----------|------------|------|------|-----------|
| **Triton** | 블록 단위 | PyTorch 연동, 컴파일러 최적화 | 블록 사고 필요, 문서 부족 | 블록 연산 중심 커스텀 커널 |
| **Numba** | 스레드 단위 | Python 친화적, GPU/CPU 모두 지원 | 저수준 제어 복잡도 | 범용 GPU 코드, 안정성 중시 |
| **OpenCL** | 스레드 단위 | 저수준 제어 | 생태계 노후화, 타입 오류 위험 | 레거시 환경, 멀티벤더 필수 |
| **CUDA** | 스레드 단위 | 최고 성능, 풍부한 생태계 | NVIDIA 전용 | NVIDIA 전용 고성능 커널 |
| **ROCm/HIP** | 스레드 단위 | CUDA 유사 문법 | AMD 전용 | AMD GPU 환경 |

**벤치마킹 시 주의사항 (이걸 빠뜨리면 결과가 쓰레기다)**

1. **워밍업 필수**: Triton은 첫 실행 시 JIT 컴파일 비용이 크다. 최소 3회 이상 실행 후 측정.
2. **캐시 플러시**: L2 캐시를 비우지 않으면 두 번째 실행이 인위적으로 빠르게 나온다.
3. **CUDA 동기화**: CUDA 커널은 비동기 실행이라 `torch.cuda.Event`로 GPU 완료 시점을 측정해야 한다.
4. **디스크 공간 확인**: Triton JIT 캐시 문제로 디스크 부족 시 성능이 50배 저하될 수 있다.

## 5. GPU 벤더 생태계 비교

OpenShift AI는 멀티벤더 GPU를 지원한다. 벤더별 특징을 알아두면 고객 환경에 맞는 조언이 가능하다.

| 벤더 | 대표 제품 | 소프트웨어 스택 | 강점 | OCP 리소스 식별자 |
|------|----------|----------------|------|-------------------|
| **NVIDIA** | A100, H100, Blackwell RTX PRO 4500 | CUDA, cuDNN, NCCL | 생태계 최강, MIG 지원 | `nvidia.com/gpu` |
| **AMD** | Instinct MI300X | ROCm, HIP, RCCL | 192GB HBM, 대형 LLM 학습 | `amd.com/gpu` |
| **Intel** | Data Center GPU Flex 140 | OpenCL, OpenVINO, oneAPI | 에너지 효율, CPU 통합 | `intel.feature.node.kubernetes.io/gpu` |

**NVIDIA Blackwell (RTX PRO 4500) 특이사항**

- NVFP4(4-bit floating point) 지원: 대형 모델을 더 적은 메모리로 추론
- CUDA 13.0, 드라이버 580.x 필요
- `kernelModuleType: open` 설정 필요 (ClusterPolicy)
- Llama-3.1-8B 기준 2개 GPU로 peak 3515 tok/s 달성

**AMD MI300X 특이사항**

- 192GB HBM으로 단일 GPU에서 70B 모델도 처리 가능
- ROCm 6.x + RHEL 9.x 조합 필요
- PyTorch 리소스 요청만 `nvidia.com/gpu` → `amd.com/gpu`로 바꾸면 기존 워크플로 재사용 가능
- OpenShift 모니터링 스택에 AMD 런타임 메트릭 통합은 아직 미완성 (2025 기준)

## 핵심 정리 (3줄 요약)

1. GPU는 수만 개 스레드로 같은 연산을 동시에 실행하는 SIMD 장치다. AI 학습의 행렬 연산에 최적화되어 있다.
2. GPU 알고리즘은 총 연산량보다 병렬 깊이(Span)를 줄이는 방향으로 설계한다. 단순 병렬화는 오히려 느릴 수 있다.
3. 프레임워크는 문제 구조에 따라 고른다. 범용이면 Numba, PyTorch 연동이면 Triton, AMD면 ROCm/HIP.
