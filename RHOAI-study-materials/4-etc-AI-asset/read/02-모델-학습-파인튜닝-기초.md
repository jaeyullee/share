# 모델 학습·파인튜닝 기초 (OpenShift AI 관점)

> OCP 엔지니어 관점 | 10분 분량

---

## 학습 vs 파인튜닝 vs 추론

| 단계 | 설명 | GPU 메모리 |
|------|------|------------|
| **사전학습** | 수조 개 토큰으로 기반 모델 생성 | 매우 많음 (수백 GPU) |
| **파인튜닝** | 특정 도메인/태스크에 맞게 추가 학습 | 추론보다 훨씬 많음 |
| **추론** | 학습된 모델로 응답 생성 | 상대적으로 적음 |

파인튜닝은 추론보다 **3~10배 이상** 메모리가 필요하다. 그래디언트, 옵티마이저 상태, 활성화 값을 모두 GPU에 올려야 하기 때문이다.

## OpenShift AI 학습 환경

### 워크벤치(Workbench)

```
워크벤치 = Jupyter Notebook + GPU + 영구 스토리지
```

데이터 과학 프로젝트(네임스페이스) 안에 워크벤치를 만들면 격리된 학습 환경이 생긴다. PyTorch 이미지를 선택하면 필요한 라이브러리가 이미 설치돼 있다.

### 학습 흐름 (YOLOv8 예시)

```
1. 프로젝트 생성 (네임스페이스 격리)
2. 워크벤치 생성 (PyTorch 이미지 + GPU)
3. Git 저장소 클론 (데이터셋 + 노트북)
4. 모델 학습 (yolov8m.pt 전이학습)
5. 결과 검증 (샘플 이미지 추론)
6. ONNX export (엣지 배포용)
```

## 파인튜닝 방식 비교

비유하자면, 사전학습 모델은 **모든 요리를 아는 셰프**다. 파인튜닝은 이 셰프에게 특정 식당의 메뉴만 집중 훈련시키는 것이다.

| 방식 | 학습 대상 | 메모리 | 특징 |
|------|-----------|--------|------|
| **SFT** | 전체 파라미터 | 가장 많음 | 최고 품질, 비용 높음 |
| **LoRA** | 저랭크 어댑터만 | 중간 | 전체의 0.3% 미만 학습 |
| **QLoRA** | LoRA + Float4 양자화 | 가장 적음 | 초기 로딩 병목 있음 |
| **OSFT** | 직교 부분공간 행렬 | 중간 | 다중 태스크 대응 |

### LoRA 실제 사례 (Llama 3.1 8B)

```
전체 파라미터: 80억 개
LoRA 학습 파라미터: 약 2,300만 개 (0.3% 미만)
GPU: 8x NVIDIA A10
학습 시간: 약 6시간 (5 epoch)
```

## GPU 메모리 추정: 파인튜닝 전 필수 작업

OOM(메모리 부족)으로 GPU 시간을 낭비하지 않으려면 사전 추정이 필수다.

### 메모리 구성 요소

```
총 메모리 = 모델 메모리
           + 그래디언트 메모리
           + 옵티마이저 메모리 (AdamW 상태값)
           + 활성화 메모리
           + 출력 메모리
           × 오버헤드 계수 (최대 1.3배)
```

### memory_estimator.py 사용법

```python
from memory_estimator import LoRAEstimator

estimator = LoRAEstimator(
    num_gpus=4,
    gpu_memory=80,  # GB
    model_path="meta-llama/Llama-3.1-8B",
    max_tokens_per_gpu=512,
    lora_r=16,
    verbose=True
)
# 출력: 하한값, 예상값, 상한값, 실행 가능 여부
```

### 메모리 절감 전략

| 방법 | 효과 |
|------|------|
| 더 작은 모델 선택 | 직접적 절감 |
| SFT → LoRA 전환 | 큰 절감 |
| `lora_r` 감소 | 소폭 절감 |
| `batch_size` 감소 | 활성화 메모리 절감 |
| `max_seq_len` 감소 | 활성화 메모리 절감 |
| Liger kernels 사용 | 출력 텐서 저장 비용 절감 |

## Ray + KubeRay: 분산 파인튜닝

단일 GPU로 감당 안 되는 모델은 분산 학습이 필요하다. OpenShift AI에서는 Ray + KubeRay 조합을 사용한다.

### 구성 요소

```
CodeFlare SDK → RayCluster 생성 (KubeRay)
Ray → 여러 GPU/노드에 학습 분산
DeepSpeed → 메모리 최적화 + 분산 학습 지원
TensorBoard → 학습 지표 시각화
S3 → 체크포인트 저장
```

### 학습 모니터링

```
Ray Dashboard: 작업 상태, 로그, 리소스 사용량
TensorBoard: loss, perplexity, epoch, duration
```

## Python 패키지 ABI 호환성

AI/ML 패키지는 대부분 C/C++ 네이티브 코드를 포함한다. 배포판이 달라지면 실행이 안 될 수 있다.

### manylinux 표준

```
manylinux1    → CentOS 5 기준 (구버전)
manylinux2010 → CentOS 6 기준
manylinux2014 → CentOS 7 / UBI 7 기준 (현재 주류)
```

pip는 wheel 태그를 보고 시스템에 맞는 패키지를 자동 선택한다. **pip를 최신 상태로 유지**해야 올바른 wheel이 설치된다.

OCP 관점에서 중요한 점: UBI 7 기반 컨테이너 이미지를 사용하면 manylinux2014 wheel과 호환성이 보장된다.

## OCP 엔지니어가 기억할 것

1. **파인튜닝 전 메모리 추정 필수**. `memory_estimator.py`로 OOM을 예방한다.
2. **LoRA가 현실적인 선택**. 전체 파라미터의 0.3%만 학습해도 실용적 성능이 나온다.
3. **Ray + KubeRay = OpenShift AI 분산 학습의 표준**. CodeFlare SDK로 클러스터를 코드로 프로비저닝한다.
4. **체크포인트는 S3에 저장**. 학습 중단 시 재시작 가능하도록 epoch마다 저장한다.
5. **UBI 기반 컨테이너 = manylinux2014 호환**. AI/ML 패키지 설치 시 호환성 문제를 줄인다.
